## 一、方案背景

### 1.1 当前问题

当前旅行规划产品的在线数据增强采用**在线搜索模式**，存在以下问题：

| 问题 | 具体表现 | 影响程度 |
|-----|---------|---------|
| **成本高** | 每次规划需调用搜索API + LLM提纯，单次成本$0.005 | 高 |
| **响应慢** | 搜索API调用2-3秒 + LLM提纯2-3秒，总耗时5-10秒 | 高 |
| **质量不稳定** | 搜索结果包含广告、软文、低质量内容，需人工审核 | 中 |
| **依赖第三方** | 依赖搜索API，API故障或限流导致功能不可用 | 中 |
| **数据不可控** | 搜索结果实时变化，难以保证数据一致性和可追溯性 | 中 |

### 1.2 方案目标

采用**基于扩充RAG知识库的检索增强生成模式**，替代在线搜索模式，实现：

- ✅ **成本降低60%**：从$0.005/次降至$0.002/次
- ✅ **性能提升50%**：响应时间从5-10秒降至2-4秒
- ✅ **质量可控**：知识库数据经过审核，质量稳定可靠
- ✅ **系统稳定**：本地服务，不依赖第三方搜索API
- ✅ **可扩展**：知识库可持续扩充和优化

```
在线搜索模式：
  每次规划 = 搜索API($0.003) + LLM提纯($0.002) = $0.005

RAG模式：
  每次规划 = 向量检索($0) + LLM生成($0.002) = $0.002
  1000次/天 = $2/天 = $60/月
  10000次/天 = $20/天 = $600/月

节省：60% 成本！
```

### 4.2 各模块详细说明

#### 模块1：查询理解与扩展

**功能**：
- 解析用户查询，提取目的地、天数、人群、预算等关键信息
- 查询扩展：同义词替换、相关景点推荐、周边城市扩展
- 实体识别：识别景点名称、城市名称、行政区划等

**实现**：
- 使用LLM进行意图识别和实体提取
- 基于行政区域数据进行查询扩展
- 支持多轮对话的上下文理解

#### 模块2：知识库检索

**功能**：
- 向量相似度检索：基于语义相似度检索相关文档
- 关键词检索：基于BM25算法的关键词匹配
- 混合检索：向量检索 + 关键词检索，加权融合
- 元数据过滤：按目的地、类别、时间等维度过滤

**实现**：
- 向量数据库：Chroma / FAISS / Milvus
- 嵌入模型：text2vec-base-chinese / BGE-large-zh
- 检索框架：LangChain / LlamaIndex
- 支持Top-K检索，默认K=10

#### 模块3：上下文重排序

**功能**：
- 对检索结果进行相关性重排序
- 去除冗余和重复内容
- 控制上下文长度，避免超出LLM窗口限制
- 提升检索结果的精准度和相关性

**实现**：
- 使用交叉编码器（Cross-Encoder）进行重排序
- 基于文档相似度进行去重
- 动态调整上下文长度，默认不超过4000 tokens

#### 模块4：增强生成

**功能**：
- 将检索到的知识作为上下文，注入LLM提示词
- LLM基于上下文生成结构化数据
- 输出：景点列表、游览顺序、耗时估算、避坑提示等
- 支持多轮对话和迭代优化

**实现**：
- LLM模型：deepseek-chat / Qwen2.5-7B / GLM-4
- 提示词工程：精心设计的RAG提示词模板
- 输出解析：结构化JSON输出，自动解析和校验
- 置信度评估：基于检索结果质量评估生成结果的置信度

#### 模块5：规划引擎增强

**功能**：
- 将RAG生成的数据注入规划引擎
- 候选池扩充：添加RAG检索到的景点
- 耗时优化：基于RAG数据优化景点游览时长
- 预约提醒：基于RAG数据生成预约提醒
- 避坑提示：基于RAG数据生成避坑提示

**实现**：
- 与现有规划引擎（itinerary_planner）集成
- 数据格式转换：RAG输出 → 规划引擎输入
- 权重配置：RAG数据 vs 预置数据的权重
- 降级策略：RAG检索失败时使用预置数据

## 五、知识库数据来源

### 5.1 数据来源分类

| 数据来源 | 数据类型 | 获取方式 | 质量评级 | 优先级 |
|---------|---------|---------|---------|--------|
| **预置数据** | 预约规则、避坑提示 | 已有数据库 | ⭐⭐⭐⭐⭐ | 高 |
| **公开数据集** | 景点介绍、旅游攻略 | 开源数据集 | ⭐⭐⭐⭐ | 高 |
| **官方渠道** | 景区官网、文旅局 | 官方API/网站 | ⭐⭐⭐⭐⭐ | 高 |
| **百科知识** | 景点百科、历史文化 | 维基百科/百度百科 | ⭐⭐⭐⭐ | 中 |
| **旅游平台** | 攻略、游记、点评 | 一次性爬取 | ⭐⭐⭐ | 中 |
| **用户贡献** | 用户上传的攻略和经验 | UGC内容 | ⭐⭐⭐ | 低 |
| **LLM生成** | 基于已有知识的扩展内容 | 大模型生成 | ⭐⭐⭐ | 低 |

### 5.2 数据获取策略

#### 第一优先级：高质量数据（立即导入）

- ✅ 已有预置数据（21条预约规则 + 38条避坑提示）
- ✅ 景区官方网站的公开信息
- ✅ 文旅局官方发布的旅游指南
- ✅ 维基百科/百度百科的景点介绍

#### 第二优先级：中等质量数据（逐步导入）

- ⏳ 开源旅游数据集（如马蜂窝公开数据）
- ⏳ 知名旅游博主的攻略文章
- ⏳ 旅游平台的精选攻略（人工审核后导入）

#### 第三优先级：补充数据（按需导入）

- 📋 用户贡献的攻略和经验（审核后导入）
- 📋 LLM生成的扩展内容（人工审核后导入）
- 📋 其他渠道的旅游相关数据

### 5.3 数据质量保障

1. **数据清洗**：去除广告、软文、重复内容
2. **数据去重**：基于语义相似度进行去重
3. **人工审核**：重要数据需人工审核确认
4. **质量评分**：基于数据来源、完整性、准确性进行评分
5. **持续优化**：根据用户反馈不断优化知识库内容

## 六、知识库分类和结构

### 6.1 知识库分类

建议将知识库分为**6个类别**，分别存储和检索：

```
travel_knowledge_base/
├── 01_attractions/          # 景点知识库
│   ├── 景点介绍、历史文化、开放时间、票价
│   ├── 游览路线、推荐时长、最佳季节
│   └── 景点层级关系（主POI/子POI）
│
├── 02_itineraries/          # 行程攻略知识库
│   ├── 经典行程、主题路线、一日游/多日游
│   ├── 游览顺序、时间安排、交通方式
│   └── 不同人群的行程推荐（亲子/情侣/老人）
│
├── 03_food/                 # 美食知识库
│   ├── 特色美食、老字号、网红餐厅
│   ├── 人均消费、推荐菜品、排队情况
│   └── 美食街区、夜市、小吃街
│
├── 04_accommodation/        # 住宿知识库
│   ├── 住宿区域推荐、酒店类型
│   ├── 价格区间、交通便利度
│   └── 不同预算的住宿建议
│
├── 05_tips/                 # 避坑提示知识库
│   ├── 防骗指南、预约提醒、交通提示
│   ├── 天气注意、安全提醒、购物避坑
│   └── 当地习俗、文化禁忌
│
└── 06_culture/              # 人文历史知识库
    ├── 历史背景、名人故事、革命先辈
    ├── 文化传统、民俗风情、地方特色
    └── 相关地名、红色旅游景点
```

### 6.2 文档结构设计

每个知识库文档包含以下字段：

```json
{
  "id": "doc_001",
  "title": "故宫博物院游览攻略",
  "category": "attractions",
  "destination": "北京",
  "tags": ["故宫", "明清皇宫", "世界文化遗产"],
  "content": "详细的文档内容...",
  "summary": "文档摘要，用于快速浏览",
  "keywords": ["故宫", "预约", "开放时间", "票价"],
  "source": "官方网站",
  "source_url": "https://www.dpm.org.cn/",
  "quality_score": 0.95,
  "review_status": "approved",
  "created_at": "2026-09-01",
  "updated_at": "2026-09-01",
  "version": "1.0"
}
```

### 6.3 向量存储结构

每个文档分段后，每个段落（Chunk）存储为一个向量：

```json
{
  "chunk_id": "chunk_001_001",
  "doc_id": "doc_001",
  "chunk_index": 1,
  "content": "段落内容...",
  "embedding": [0.1, 0.2, ..., 0.9],
  "metadata": {
    "category": "attractions",
    "destination": "北京",
    "tags": ["故宫", "预约"],
    "source": "官方网站",
    "quality_score": 0.95
  }
}
```

### 8.1 核心组件选型

| **嵌入模型** | text2vec-base-chinese | BGE-large-zh / M3E | text2vec-base-chinese中文语义嵌入效果好，模型体积适中，推理速度快 |
| **LLM模型** | deepseek-chat | Qwen2.5-7B / GLM-4 | deepseek-chat生成质量高，成本低，支持长上下文；Qwen2.5-7B可本地部署 |

### 8.2 技术栈详情

#### 向量数据库：Chroma

**优势**：
- 轻量级，Python原生支持
- 支持持久化存储
- 内置嵌入模型支持
- API简单易用
- 适合中小规模应用（百万级向量）

**部署方式**：
```python
import chromadb

# 客户端初始化
client = chromadb.PersistentClient(path="./data/chroma")

# 创建集合
collection = client.create_collection(
    name="travel_knowledge",
    metadata={"hnsw:space": "cosine"}
)
```

#### 嵌入模型：text2vec-base-chinese

**优势**：
- 专门针对中文语义优化
- 模型体积适中（~400MB）
- 推理速度快（CPU可运行）
- 语义相似度计算准确
- 支持句向量和段落向量

**使用方式**：
```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer('shibing624/text2vec-base-chinese')
embeddings = model.encode(["故宫博物院", "天安门广场"])
```

#### LLM模型：deepseek-chat

**优势**：
- 生成质量高，中文理解能力强
- 成本低（~$0.002/1K tokens）
- 支持长上下文（64K tokens）
- API兼容OpenAI格式
- 响应速度快

**使用方式**：
```python
from openai import OpenAI

client = OpenAI(
    api_key="your_api_key",
    base_url="https://api.deepseek.com/v1"
)

response = client.chat.completions.create(
    model="deepseek-chat",
    messages=[
        {"role": "system", "content": "你是一个旅行规划助手"},
        {"role": "user", "content": "北京3天行程规划"}
    ]
)
```

## 十、总结和建议

### 10.1 方案总结

采用**基于扩充RAG知识库的检索增强生成模式**，替代在线搜索模式，可以：

- ✅ **成本降低60%**：从$0.005/次降至$0.002/次
- ✅ **性能提升50%**：响应时间从5-10秒降至2-4秒
- ✅ **质量可控**：知识库数据经过审核，质量稳定可靠
- ✅ **系统稳定**：本地服务，不依赖第三方搜索API
- ✅ **可扩展**：知识库可持续扩充和优化

### 10.2 实施建议

**强烈建议采用RAG方案替代在线搜索**，采用**渐进式实施**策略：

1. **第一阶段（1-2周）**：搭建基础RAG框架，导入预置数据，验证基础流程
2. **第二阶段（2-3周）**：扩充知识库内容，数据量达到1000+条
3. **第三阶段（1-2周）**：优化检索算法，检索准确率达到85%+
4. **第四阶段（持续）**：深度集成规划引擎，建立持续运营机制

**在线搜索作为备选方案**：
- 在知识库没有相关数据时，降级使用在线搜索
- 在线搜索获取的数据经过审核后，加入知识库
- 逐步减少对在线搜索的依赖

### 10.3 关键成功因素

1. **知识库质量**：高质量的知识库是RAG成功的基础
2. **检索准确率**：准确的检索是生成高质量结果的前提
3. **提示词工程**：精心设计的提示词能充分发挥LLM能力
4. **持续优化**：根据用户反馈不断迭代优化
5. **成本控制**：严格控制LLM调用频率和费用
