## 2. P1优先级优化

### 2.1 知识时效性标注

#### 优化目标

区分人文知识库中的**静态知识**和**动态信息**，对动态信息标注更新时间，提醒用户核实，避免因信息过时导致用户行程受影响。

#### 问题背景

当前知识库中的所有信息都一视同仁，但实际上：
- **静态知识**（历史沿革、建筑格局、文化意义、名人典故）：几乎不会变化，可信度高
- **动态信息**（开放时间、门票价格、临时闭园、交通管制）：可能随时变化，需要标注时效性

例如：故宫的门票价格、预约规则可能调整，如果知识库中的信息过时，可能导致用户白跑一趟。

#### 具体实现方案

##### 2.1.1 数据结构扩展

在 `MainPOI` 和 `InnerPOI` 数据结构中新增时效性字段：

```python
class TimelinessInfo:
    """时效性信息"""
    is_static: bool = True              # 是否为静态知识
    last_updated: str = ""              # 最后更新时间（YYYY-MM-DD）
    update_frequency: str = "yearly"    # 更新频率：daily/weekly/monthly/yearly/never
    source: str = ""                     # 信息来源（官方网站/携程/马蜂窝等）
    verification_status: str = "unverified"  # 验证状态：verified/unverified/outdated
```

在 `MainPOI` 中新增：
- `opening_hours`: 开放时间（动态）
- `ticket_price`: 门票价格（动态）
- `booking_required`: 是否需要预约（动态）
- `timeliness`: 时效性信息对象

##### 2.1.2 分块级时效性标注

在RAG向量化时，每个文档块的metadata中新增时效性字段：

```python
metadata = {
    "poi_name": "故宫",
    "chunk_type": "visit_guide",
    "importance": "high",
    "timeliness": {
        "is_static": False,
        "last_updated": "2026-08-01",
        "update_frequency": "monthly",
        "verification_status": "verified"
    }
}
```

##### 2.1.3 检索时时效性过滤和排序

在 `Retriever` 中新增时效性感知的检索策略：
- 静态知识优先返回（可信度高）
- 动态信息标注"信息更新于XXXX年XX月，请以官方为准"
- 超过更新周期的动态信息自动标记为"可能已过时"

##### 2.1.4 前端展示优化

在AI讲解弹窗和点位卡片中：
- 静态知识正常展示
- 动态信息（开放时间、门票价格）旁显示"更新于2026-08"标签
- 超过3个月未更新的动态信息显示黄色警告"信息可能已更新，请核实"
- 超过6个月未更新的显示红色警告"信息可能已过时"

#### 涉及文件

- `backend/app/data/poi_hierarchy.py` - 数据结构扩展
- `backend/app/services/rag/vector_store.py` - metadata扩展
- `backend/app/services/rag/retriever.py` - 时效性感知检索
- `backend/app/services/rag/generator.py` - 生成时标注时效性
- `frontend/src/components/DayCard.vue` - 前端展示优化
- `frontend/src/components/AiExplainModal.vue` - AI讲解弹窗优化

#### 预计工作量

- 后端数据结构扩展：2小时
- 时效性标注逻辑：4小时
- 检索策略优化：3小时
- 前端展示优化：4小时
- 测试验证：3小时
- **合计：约16小时（2人天）**

#### 预期效果

- 用户可清晰区分哪些信息是可靠的历史文化知识，哪些是需要核实的实用信息
- 避免因门票价格、开放时间等动态信息过时而影响用户行程
- 提升产品的专业度和可信度

### 2.2 AI讲解前端体验优化

#### 优化目标

提升AI讲解功能的前端用户体验，增加讲解风格选择、语音播报、讲解收藏等功能，让AI讲解从"能用"变成"好用"。

#### 问题背景

当前AI讲解功能已实现后端能力，但前端体验较为基础：
- 仅支持默认讲解风格，无法根据用户偏好切换
- 仅文字展示，无语音播报，不适合边走边听
- 无收藏功能，用户喜欢的讲解无法保存
- 弹窗交互较简单，无目录导航、字号调节等

#### 具体实现方案

##### 2.2.1 讲解风格选择

在AI讲解弹窗顶部增加风格切换Tab：
- **默认风格**：全面均衡，适合大多数用户
- **历史深度**：侧重历史沿革、文化背景、名人典故
- **摄影打卡**：侧重拍照机位、最佳时间、构图建议
- **亲子友好**：语言通俗，增加互动问题，适合带孩子
- **快速导览**：精简版，只讲重点，3分钟读完

实现方式：
- 后端 `generate_poi_explanation` 接口已支持 `style` 参数
- 前端切换风格时重新调用接口生成对应风格讲解
- 缓存已生成的风格，避免重复调用

##### 2.2.2 语音播报

增加文字转语音（TTS）功能：
- 使用浏览器内置 `SpeechSynthesis` API（免费，无需额外依赖）
- 讲解内容分段播报，当前朗读段落高亮
- 支持播放/暂停/停止/上一段/下一段控制
- 支持语速调节（0.5x - 2x）
- 支持音色选择（浏览器可用的中文语音）

实现方式：
```javascript
const synth = window.speechSynthesis;
const utterance = new SpeechSynthesisUtterance(text);
utterance.lang = 'zh-CN';
utterance.rate = 1.0;
synth.speak(utterance);
```

##### 2.2.3 讲解收藏

增加讲解收藏功能：
- 用户可收藏喜欢的景点讲解
- 收藏的讲解保存在用户画像中（后端持久化）
- "我的"页面增加"我的收藏"入口，查看所有收藏的讲解
- 收藏的讲解可离线查看（已生成的内容缓存到本地）

实现方式：
- 后端新增 `POST /api/profile/favorites` 接口
- 收藏数据结构：`{poi_name, style, content, created_at}`
- 前端收藏按钮（心形图标），点击收藏/取消

##### 2.2.4 讲解弹窗交互优化

- **目录导航**：左侧固定目录，点击跳转到对应模块（一句话定位/历史沿革/建筑格局/...）
- **字号调节**：A- / A+ 按钮，调节讲解文字大小
- **分享功能**：生成讲解分享卡片（图片），可分享到微信/朋友圈
- **反馈功能**：讲解内容底部增加"有帮助/没帮助"反馈按钮，用于优化讲解质量
- **加载优化**：骨架屏加载，避免白屏等待

#### 涉及文件

- `frontend/src/components/DayCard.vue` - AI讲解按钮和弹窗
- `frontend/src/components/AiExplainModal.vue` - 新建独立的AI讲解弹窗组件
- `frontend/src/api/index.js` - 新增收藏相关API
- `backend/app/routers/profile.py` - 新增收藏接口
- `backend/app/services/user_profile.py` - 收藏数据管理

#### 预计工作量

- 讲解风格选择：3小时
- 语音播报：4小时
- 讲解收藏：5小时（前后端）
- 弹窗交互优化：6小时
- 测试验证：3小时
- **合计：约21小时（2.5人天）**

#### 预期效果

- AI讲解功能从"基础可用"升级为"体验优秀"
- 语音播报让用户可以边走边听，提升实际使用场景的适配性
- 讲解风格选择满足不同用户的个性化需求
- 收藏功能提升用户粘性和产品价值

## 3. P2优先级优化

### 3.1 知识更新机制

#### 优化目标

建立人文知识库的定期更新机制，确保开放时间、门票价格等动态信息的时效性，支持手动刷新和自动更新。

#### 问题背景

当前知识库数据是静态的，一旦录入就不会更新。但实际上：
- 景点门票价格可能调整
- 开放时间可能随季节变化
- 可能有临时闭园、维修等情况
- 周边商业可能开业或关闭

如果信息长期不更新，可能误导用户。

#### 具体实现方案

##### 3.1.1 更新策略设计

| 信息类型 | 更新频率 | 更新方式 | 优先级 |
|---|---|---|---|
| 历史沿革/建筑格局 | 永不更新 | 手动 | 低 |
| 文化意义/名人典故 | 每年 | 手动 | 低 |
| 内部动线/游玩重点 | 每半年 | 手动+自动 | 中 |
| 周边景点/美食街 | 每季度 | 自动 | 中 |
| 开放时间 | 每月 | 自动 | 高 |
| 门票价格 | 每月 | 自动 | 高 |
| 预约规则 | 每周 | 自动 | 高 |
| 临时闭园/活动 | 每天 | 自动 | 最高 |

##### 3.1.2 自动更新数据源

- **高德地图API**：POI信息（地址、电话、营业时间）
- **携程/马蜂窝爬虫**：门票价格、用户评价、热门程度
- **景区官方网站**：公告、临时闭园、活动信息
- **天气API**：天气对景区开放的影响（如暴雨关闭）

##### 3.1.3 更新流程设计

```
1. 定时任务触发（每天凌晨2点）
   ↓
2. 检查需要更新的景点（按更新频率）
   ↓
3. 从数据源获取最新信息
   ↓
4. 与现有信息对比，检测变化
   ↓
5. 如有变化，生成更新建议
   ↓
6. 人工审核（高优先级信息）或自动更新（低优先级）
   ↓
7. 更新向量库（重新向量化变更的文档块）
   ↓
8. 记录更新日志
```

##### 3.1.4 手动刷新功能

- 管理员后台增加"知识库管理"页面
- 每个景点显示最后更新时间和更新状态
- 支持手动刷新单个景点或批量刷新
- 支持查看更新历史和变更对比

##### 3.1.5 更新日志和审计

- 每次更新记录：更新时间、更新内容、变更前后对比、操作人
- 支持回滚到历史版本
- 更新统计：本月更新了多少个景点、多少条信息

#### 涉及文件

- `backend/app/services/rag/knowledge_updater.py` - 新建知识更新服务
- `backend/app/services/rag/knowledge_service.py` - 扩展更新相关方法
- `backend/app/routers/rag.py` - 新增更新管理接口
- `backend/app/data/update_log.py` - 新建更新日志数据结构
- `frontend/src/views/admin/KnowledgeManage.vue` - 新建知识库管理页面
- `backend/requirements.txt` - 可能新增定时任务依赖（APScheduler）

#### 预计工作量

- 更新策略设计和数据结构：4小时
- 自动更新服务（数据源对接）：8小时
- 更新流程和对比逻辑：6小时
- 手动刷新功能（前后端）：5小时
- 更新日志和审计：4小时
- 测试验证：5小时
- **合计：约32小时（4人天）**

#### 预期效果

- 知识库动态信息保持时效性，避免误导用户
- 自动更新减少人工维护成本
- 更新日志和审计保证数据质量可控
- 管理员可清晰了解知识库的健康状态

### 3.2 用户画像前端体验优化

#### 优化目标

提升用户画像功能的前端用户体验，增加偏好编辑、画像分享、偏好重置等功能，让用户画像从"被动学习"变成"主动可管理"。

#### 问题背景

当前用户画像功能已实现后端能力（自动学习偏好、跨行程记忆），但前端体验较为基础：
- 仅展示已学习到的偏好，用户无法主动编辑
- 无画像分享功能，用户无法展示自己的旅行人格
- 无偏好重置功能，用户想重新开始时无法清空
- 偏好学习过程不透明，用户不知道系统是如何学习的

#### 具体实现方案

##### 3.2.1 偏好编辑功能

在"我的旅行偏好"卡片中增加编辑功能：
- 每项偏好可点击编辑（下拉选择或标签选择）
- 支持手动添加/删除旅行风格标签
- 编辑后的偏好立即生效，影响后续行程规划
- 区分"系统学习"和"用户手动设置"的偏好（手动设置的优先级更高）

实现方式：
- 后端 `PUT /api/profile/preferences` 接口，支持更新偏好
- 前端编辑模式，点击"编辑"按钮进入编辑状态
- 保存后调用接口更新，同时更新本地缓存

##### 3.2.2 画像分享功能

生成用户旅行画像分享卡片：
- 画像卡片内容：用户名、旅行人格标签（如"人文探索者""美食猎人""自然风光爱好者"）、去过的城市数、总行程数、偏好关键词云
- 支持生成图片（使用html2canvas），可保存到本地或分享到社交平台
- 支持生成分享链接，其他用户可查看你的旅行画像（可选公开/私密）

实现方式：
- 后端 `GET /api/profile/share-card` 接口，返回分享卡片数据
- 前端使用html2canvas生成图片
- 旅行人格标签算法：根据用户偏好自动匹配（如人文历史占比高→"人文探索者"）

##### 3.2.3 偏好重置功能

- 增加"重置偏好"按钮（在设置中，需二次确认）
- 重置后清空所有已学习的偏好，恢复到初始状态
- 保留用户的行程历史和足迹，仅清空偏好
- 重置后提示用户"偏好已重置，下次规划将重新学习你的偏好"

##### 3.2.4 偏好学习过程可视化

让用户了解系统是如何学习偏好的：
- 每项偏好显示"学习来源"（如"从3次规划中学习"、"从5次调整中学习"）
- 显示偏好学习时间线（什么时候学习了什么偏好）
- 支持"忽略此偏好"，用户可以告诉系统不要学习某项偏好

##### 3.2.5 偏好影响力展示

展示用户偏好如何影响行程规划：
- 在行程规划结果中，标注"根据你的偏好，我们优先选择了XXX"
- 对比展示：如果没有偏好，行程会是什么样；有了偏好，行程有什么不同
- 让用户直观感受到偏好学习的价值

#### 涉及文件

- `frontend/src/views/Me.vue` - 用户画像页面优化
- `frontend/src/components/ProfileEditor.vue` - 新建偏好编辑组件
- `frontend/src/components/ProfileShareCard.vue` - 新建画像分享卡片组件
- `frontend/src/api/index.js` - 新增偏好编辑/分享/重置API
- `backend/app/routers/profile.py` - 新增偏好管理接口
- `backend/app/services/user_profile.py` - 扩展偏好管理方法

#### 预计工作量

- 偏好编辑功能：5小时
- 画像分享功能：6小时
- 偏好重置功能：2小时
- 学习过程可视化：4小时
- 偏好影响力展示：4小时
- 测试验证：3小时
- **合计：约24小时（3人天）**

#### 预期效果

- 用户画像从"黑盒"变成"透明可管理"
- 用户可主动塑造自己的旅行偏好，提升规划准确度

- 偏好学习过程可视化提升用户信任感

## 4. P3优先级优化

### 4.1 多模态知识支持

#### 优化目标

在文本知识基础上，增加图片、音频等多模态人文知识，提升讲解的丰富度和沉浸感。

#### 具体实现方案

##### 4.1.1 图片知识

- 每个景点增加配图：景区全景、标志性建筑、四季风光、历史老照片
- 图片存储：本地存储或对象存储（OSS），向量库中存储图片URL和描述
- 图片检索：支持以文搜图（输入描述，找到相关图片）和以图搜图（上传图片，找到相似景点）
- 前端展示：AI讲解中穿插相关图片，点击可放大查看

##### 4.1.2 音频知识

- 每个景点增加语音讲解：专业播音员录制的景点介绍（可使用TTS生成）
- 历史语音：历史事件的原声重现（如开国大典、名人演讲）
- 前端展示：讲解中可播放音频，支持边听边看文字

### 4.2 知识库持续扩展

#### 优化目标

持续扩展人文知识库的覆盖范围，从当前28个景区扩展到全国主要5A/4A景区。

#### 扩展路线图

| 阶段 | 目标景区数 | 覆盖范围 | 时间 |
|---|---|---|---|
| 第一阶段（已完成） | 28个 | 17个热门城市的标志性景区 | 2026-08 |
| 第二阶段 | 50个 | 全国5A景区（约300个中的前50个热门） | 2026-09 |
| 第三阶段 | 100个 | 全国主要5A景区 + 热门4A景区 | 2026-10 |
| 第四阶段 | 200个 | 全国5A景区全覆盖 + 重点4A景区 | 2026-12 |
| 第五阶段 | 500+ | 全国主要景区全覆盖 | 2027-Q1 |

#### 数据采集方式

1. **人工编辑**：高质量景区（如故宫、西湖）由人工编辑，确保内容质量
2. **AI辅助生成**：使用LLM基于公开资料生成初稿，人工审核后入库
3. **爬虫采集**：从携程、马蜂窝、百度百科等平台采集基础信息，自动生成结构化数据
4. **用户贡献**：开放用户投稿通道，用户可提交景区知识，审核后入库

#### 数据质量保证

- 每个景区数据必须包含：简介（200字以上）、内部动线（3站以上）、周边景点（2处以上）、避坑提示（3条以上）
- 数据审核流程：AI生成 → 自动校验（完整性/准确性）→ 人工抽检 → 入库
- 定期数据质量评估：抽查景区数据，评估内容准确性和丰富度

#### 涉及文件

- `backend/app/data/poi_hierarchy_extra.py` - 持续补充景区数据
- `backend/app/data/poi_hierarchy_batch2.py` - 新建第二批数据文件
- `backend/app/data/poi_hierarchy_batch3.py` - 新建第三批数据文件
- `docs/knowledge-base-quality-standards.md` - 新建数据质量标准文档

#### 预计工作量

- 每增加10个景区：约8小时（1人天，含数据采集、编辑、审核、导入）
- 扩展到50个：+22个景区，约18小时（2人天）
- 扩展到100个：+50个景区，约40小时（5人天）
- **长期持续投入**

## 5. 其他优化方向

### 5.1 RAG检索效果优化

- **重排序（Rerank）**：引入bge-reranker模型，对初筛结果进行二次排序，提升检索准确度
- **查询改写（Query Rewriting）**：使用LLM改写用户查询，扩展同义词、纠正错别字，提升召回率
- **混合检索权重调优**：调整向量检索和关键词检索的权重比例，找到最佳平衡点
- **知识库分块策略优化**：调整分块大小和重叠比例，提升检索的精准度

### 5.2 AI讲解质量优化

- **讲解模板优化**：优化不同风格的讲解模板，提升内容的逻辑性和可读性
- **事实准确性校验**：对AI生成的讲解进行事实校验，避免幻觉
- **个性化讲解**：结合用户画像，生成个性化的讲解内容（如对历史爱好者多讲历史）
- **多语言讲解**：支持英文、日文等多语言讲解，服务国际游客

### 5.3 性能优化

- **向量库索引优化**：使用HNSW索引，提升检索速度
- **模型量化**：对Embedding模型进行量化（INT8），减少内存占用，提升推理速度
- **缓存策略优化**：增加热点景点讲解的缓存，减少重复生成
- **批量导入优化**：优化知识库批量导入的速度，支持增量导入

### 5.4 安全和隐私

- **内容安全审核**：对用户提交的知识和AI生成的讲解进行内容安全审核
- **用户数据隐私**：用户画像数据加密存储，支持用户导出和删除自己的数据
- **API访问控制**：RAG接口增加限流和访问控制，防止滥用

## 7. 验收标准

### 7.1 知识时效性标注验收标准

- [ ] 所有动态信息（开放时间、门票价格、预约规则）均标注更新时间
- [ ] 超过3个月未更新的动态信息显示黄色警告
- [ ] 超过6个月未更新的显示红色警告
- [ ] 静态知识和动态信息在展示上有明确区分
- [ ] 用户可清晰看到每条信息的最后更新时间

### 7.2 AI讲解前端体验验收标准

- [ ] 支持至少4种讲解风格切换（默认/历史/摄影/亲子）
- [ ] 语音播报功能正常，支持播放/暂停/语速调节
- [ ] 讲解收藏功能正常，收藏的讲解可在"我的"页面查看
- [ ] 讲解弹窗有目录导航，点击可跳转
- [ ] 加载状态有骨架屏，无白屏

### 7.3 知识更新机制验收标准

- [ ] 定时任务可自动检查需要更新的景点
- [ ] 可从至少2个数据源获取最新信息
- [ ] 变更检测逻辑准确，能识别信息变化
- [ ] 管理员后台可手动刷新单个或批量景点
- [ ] 更新日志完整记录每次更新的内容和操作人

### 7.4 用户画像前端体验验收标准

- [ ] 用户可手动编辑所有偏好项
- [ ] 手动设置的偏好优先级高于系统学习
- [ ] 画像分享卡片可生成图片并保存
- [ ] 偏好重置功能正常，重置后恢复初始状态
- [ ] 每项偏好显示学习来源和学习时间

### 7.5 知识库扩展验收标准

- [ ] 每个新增景区数据完整（简介+内部动线+周边+避坑提示）
- [ ] 新增景区数据通过质量审核
- [ ] 向量库导入成功，可正常检索
- [ ] 名称模糊匹配覆盖新增景区的常见别名
