## 阶段一：用户输入与意图识别

| 步骤 | 数据转变 | 数据来源 | 关键函数/文件 |
|---|---|---|---|
| **1. 用户输入** | 原始文本消息（如"去济南玩3天"） | 用户前端输入 | `ChatPlanRequest.messages` |
| **2. 提取用户消息** | 从对话历史中提取所有role=user的消息内容 | 前端传入的对话历史 | `chat_plan()` 第348行 |
| **3. LLM意图识别** | 原始文本 → `{intent, args, reply, confidence, source}` | **本地LLM模型**（qwen2:7b）+ 意图识别Skill | `_llm_chat_plan()` → `IntentRecognizer.recognize()` |
| **4. 意图分类路由** | 根据intent字段分流：<br>- `plan` → 行程规划<br>- `chat` → 普通对话<br>- `weather` → 天气查询<br>- `poi` → 景点搜索 | LLM输出的intent字段 | `_llm_chat_plan()` 第96-180行 |
| **5. 规则兜底（可选）** | 如果LLM不可用或解析失败，使用规则解析 | **规则引擎**（关键词匹配） | `parse_intent()` → `legacy_parser.py` |

### 意图类型说明

| 意图类型 | 触发场景 | 后续处理 |
|---|---|---|
| `plan` | 用户明确要求规划行程（如"去X玩N天"） | 进入行程规划流程 |
| `chat` | 普通咨询、闲聊、人文介绍 | LLM直接回复，不生成行程 |
| `weather` | 询问天气（如"济南天气怎么样"） | 调用天气API，LLM组织回复 |
| `poi` | 搜索景点/美食/购物（如"杭州有什么好玩的"） | 调用POI搜索API，LLM组织回复 |

### 通用POI去重算法

```
输入：候选景点列表
输出：去重后的景点列表 + 被移除的重复景点详情

算法步骤：
1. 按评分降序排序（高分优先保留）
2. 两两比较景点：
   a. 坐标距离 < 200米 → 可能是同一景点
   b. 名称包含关系（A包含B或B包含A）→ 可能是主景区和子景点
   c. 名称相似度 > 0.8（编辑距离算法）→ 可能是同一景点不同命名
3. 如果满足以上任一条件，保留评分较高的景点，移除评分较低的景点
4. 记录被移除的景点详情（removed, kept, reason）
```

### 地理聚类算法（traditional策略）

```
输入：候选景点列表、天数、城市中心坐标
输出：按天分组的行程计划

算法步骤：
1. 识别顶级地标（must_visit标记），作为每天的核心锚点
2. 将顶级地标按地理距离聚类，分配到不同天
3. 对每一天，以锚点为中心，按距离从近到远选择其他景点
4. 每天景点数量根据策略配置和体验曲线调整
5. 跨天去重：确保不同天不出现同一景点或同一地标系列
6. 跨天地域去重：确保不同天的景点不在同一子区域
```

### 两阶段规划算法（spatial_temporal策略）

```
阶段一：空间整体路线规划
1. 解析出发点和返程点的地理坐标
2. 以出发点 → 目的城市（多个景点）→ 返程点的顺序，规划整体空间路线
3. 使用最近邻算法（TSP近似）优化景点间的路径
4. 生成空间路线摘要

阶段二：按时间拆分
1. 根据总天数，将空间路线均匀拆分为N段
2. 每段对应一天的行程
3. 确保每天的景点数量合理（根据体验曲线调整）
4. 住宿点推荐：每天景点聚类中心附近区域
```

### 体验曲线配置

| 天数位置 | 强度等级 | 推荐景点数 | 说明 |
|---|---|---|---|
| 第1天 | 低强度 | 2-3个 | 轻松入门，适应当地环境 |
| 第2-3天 | 高强度 | 4-5个 | 核心景点，体力充沛时游览 |
| 第4-5天 | 中等强度 | 3-4个 | 持续游览，注意休息 |
| 第6天+ | 低强度 | 2-3个 | 轻松收尾，预留返程时间 |

### 景点强度判断

| 强度等级 | 判断关键词 | 示例 |
|---|---|---|
| 高强度 | 长城、泰山、黄山、华山、张家界、故宫、颐和园、兵马俑、爬山、徒步、登山 | 八达岭长城、泰山风景区 |
| 中等强度 | 博物馆、历史、文化、古迹、寺庙、园林、古镇 | 故宫博物院、苏州园林 |
| 低强度 | 公园、广场、步行街、购物、美食、咖啡馆 | 王府井步行街、南锣鼓巷 |

## 阶段七：行程完善与返回

| 步骤 | 数据转变 | 数据来源 | 关键函数/文件 |
|---|---|---|---|
| **33. 天气查询** | 城市名 → 实时天气数据（天气、气温、风力、温馨提示） | 腾讯/高德地图天气API + TTL缓存（2小时） | `amap.weather()` 第621行 |
| **34. 预算估算** | 行程数据 → 总预算 + 分项预算（住宿/餐饮/交通/门票） | **规则引擎** 预算计算规则 + 景点价格/评分 | `build_plan()` 预算计算部分 |
| **35. 交通建议** | 景点间距离 → 通行建议（步行/地铁/公交/打车/自驾） | 景点坐标距离 + 出行方式参数 | `_geo_plan()` 内部 |
| **36. 住宿区域推荐** | 每天景点聚类中心 → 推荐住宿区域（不推荐具体酒店） | 景点坐标聚类中心 | `_geo_plan()` 内部 |
| **37. LLM生成人文回复** | 行程数据 → 有人文介绍的自然语言回复 | **本地LLM模型** + 行程数据 + RAG知识库（可选） | `ai_mod.generate_plan_reply()` 第436-452行 |
| **38. 行程保存** | 完整行程数据 → 保存到数据库（itinerary_sessions表）<br>关联用户ID和对话ID | **数据库** `itinerary_sessions`表 | `SessionStore` / itinerary API |
| **39. 返回前端** | `ChatPlanResponse(ready, reply, params, plan)`<br>plan包含：destination, days, day_plans, all_pois, total_budget, city_center, weather等 | 所有前面步骤的结果汇总 | `chat_plan()` 返回 |

### 预算估算规则

| 预算项目 | 计算方式 | 说明 |
|---|---|---|
| 住宿 | 天数 × 每晚预算 | 根据预算档位：经济200-300/适中350-550/舒适600-1000 |
| 餐饮 | 天数 × 人数 × 每天餐饮预算 | 经济80-120/适中120-200/舒适200-400 |
| 交通 | 市内交通 + 景点间交通 | 市内50-80/天，景点间根据距离估算 |
| 门票 | 景点门票价格汇总 | 根据景点price字段，无价格则按类别估算 |
| 其他 | 总预算 × 10% | 购物、纪念品、应急费用 |
