# 从用户输入到行程规划生成的完整流程

## 流程总览

```
用户输入 → 前端发送 → API入口 → 意图识别 → 意图路由 → 行程规划 → LLM回复 → 前端展示
```

---

## 阶段1：前端用户输入

**文件**：`frontend-app/src/components/ChatPlanner.vue`

### 逻辑
1. 用户在对话框中输入自然语言（如"帮我规划北京3天行程"）
2. 前端将用户消息加入对话历史
3. 发送POST请求到 `/api/chat/plan`，携带 `messages` 数组

### 请求结构
```json
{
  "messages": [
    {"role": "user", "content": "帮我规划北京3天行程"}
  ]
}
```

---

## 阶段2：后端API入口

**文件**：`backend/app/api/plan.py`

### 主函数：`chat_plan()`
1. 接收请求，提取用户消息数组
2. 调用 `_llm_chat_plan()`（主路径，LLM意图识别）
3. 如果主路径失败，调用 `_fallback_plan()`（降级路径，规则引擎）

### 降级函数：`_fallback_plan()`
- 使用规则引擎解析意图（`parse_intent`）
- 如果是plan意图，直接调用 `build_plan()`
- 如果是chat意图，调用 `chat_reply()`

---

## 阶段3：意图识别（LLM）

**文件**：`backend/app/ai/ai.py`
**函数**：`analyze_intent(messages)`

### 意图分类（4种）
| 意图 | 说明 | 触发条件 |
|------|------|---------|
| `chat` | 普通对话/寒暄 | 纯寒暄、不确定意图（安全默认） |
| `plan` | 行程规划 | 有明确"去X玩/规划/行程"等动作+目的地 |
| `weather` | 天气查询 | 有明确天气关键词+城市 |
| `poi` | 景点搜索 | 有明确"有什么好玩的/推荐"等动作+城市 |

### 置信度规则（非常重要）
```
confidence >= 0.7 → 允许返回 plan/weather/poi
confidence < 0.7  → 必须返回 chat（安全默认）
```

### 核心规则
1. **只分析当前消息**，完全忽略历史消息的内容、地点和话题
2. 只取最近2条消息（1条历史+1条当前），避免过长历史干扰
3. 不确定时一律返回chat，避免误判
4. 意图必须是单一值，严禁组合值（如"weather|plan"）

### 输出结构
```json
{
  "intent": "plan",
  "args": {
    "destination": "北京",
    "days": 3,
    "travelers": 1,
    "budget_level": "适中",
    "style": "综合",
    "pace": "适中",
    "traffic_mode": "公共交通",
    "interests": []
  },
  "reply": "",
  "confidence": 0.9
}
```

---

## 阶段4：意图路由

**文件**：`backend/app/api/plan.py`
**函数**：`_llm_chat_plan()`

### 路由逻辑

| 意图 | 处理方式 |
|------|---------|
| `chat` | 调用 `chat_reply()` 生成普通对话回复 |
| `weather` | 调用地图服务天气查询，LLM生成天气回复 |
| `poi` | 调用地图服务POI搜索，LLM生成景点推荐回复 |
| `plan` | 进入行程规划流程（阶段5） |

### chat意图的额外能力
- **RAG检索**：检测用户消息中的景点，检索人文知识库
- **历史名人检测**：检测历史名人/革命先辈，关联相关地名和出行推荐
- 这些能力只在chat意图中生效

---

## 阶段5：行程规划（核心引擎）

**文件**：`backend/app/core/planner.py`
**函数**：`build_plan(req: PlanRequest)`

### 输入参数
```python
PlanRequest(
    destination: str,           # 目的地（必须）
    days: int,                  # 天数（默认2-3天）
    origin: str = "",           # 出发点（可选）
    return_point: str = "",     # 返回点（可选）
    travelers: int = 1,         # 人数（默认1人）
    group_type: str = "单人",    # 出行类型
    budget_level: str = "适中",  # 预算档位
    style: str = "综合",         # 旅行风格
    pace: str = "适中",          # 节奏
    traffic_mode: str = "公共交通", # 出行方式
    exclude_poi: list = [],      # 排除的景点
    plan_strategy: str = "traditional" # 规划策略
)
```

---

### 步骤5.1：目的地定位（地理编码）

**函数**：`amap.geocode(destination)`

#### 逻辑
1. 优先在本地行政区域数据中检索（`geo_local.lookup()`）
2. 本地检索失败，调用高德/腾讯地图API地理编码
3. 获取目的地的经纬度、省市区、adcode

#### 规则
- **中国区域校验**：仅规划中国境内目的地，境外返回错误提示
- **同名地点处理**：当地名存在重复时，优先以目的地的地点为先，或通过用户对话确认
- **LLM推断行政区域**：当只有一个地点但没有前置定语时，LLM先推断地点所属的行政区域

#### 失败处理
- 无法识别目的地 → 返回错误提示，建议更具体的地址

---

### 步骤5.2：POI检索（候选池）

**函数**：`amap.search_pois(destination, center, categories)`

#### 检索类别
```python
["景点", "美食", "购物", "夜生活"]
```

#### 规则
- **景点**：构成主线规划
- **美食/购物/夜生活**：只做辅助池，不参与主线路径规划
- 应用排除规则（`exclude_poi`）

#### 缓存策略
- POI搜索结果缓存1天（TTL缓存）
- 减少第三方API调用

---

### 步骤5.3：天气查询

**函数**：`amap.weather(destination, adcode)`

#### 规则
- 获取目的地实时天气
- 天气信息用于行程展示和建议
- 天气缓存2小时

---

### 步骤5.4：行政分级枚举景点（核心）

**函数**：`_enumerate_scoped_attractions(geo, center)`

#### 枚举策略（按行政等级）

| 目的地等级 | 枚举策略 |
|-----------|---------|
| **省级** | 枚举省内所有城市，按市分隔做路径规划 |
| **市级** | 1级推荐：当前市的景点；补充：当前省的其他景点 |
| **区级/地点级** | 1级推荐：当前区/地点的景点；补充：当前市、当前省的景点 |

#### 具体规则
1. **区县→市→省三级枚举**，景点构成主线
2. **跨城污染过滤**：通过cityname字段过滤，避免第一天杭州、第二天绍兴但包含杭州地点
3. **就近优先**：距离中心点近的景点优先
4. **评分优先**：高评分景点优先
5. **本地数据优先**：优先在本地行政区域数据中检索，失败再调用高德API

---

### 步骤5.5：必打卡地标注入

**函数**：`_inject_must_visit_attrs(destination, attrs)`

#### 数据源
- `backend/app/data/static/must_visit.py` - 必打卡地标知识库
- 已迁移到数据库 `must_visit` 表

#### 规则
1. 根据目的地匹配必打卡地标
2. 如北京：天安门、故宫、长城、颐和园、天坛
3. 如杭州：西湖、灵隐寺、雷峰塔
4. 确保顶级景点不会被遗漏
5. 注入时间提前：让时间跨度收束与规划都基于完整景点池

---

### 步骤5.6：大型景区识别与权重调整

**函数**：`is_large_scenic_area()`, `is_inside_large_scenic_area()`

#### 规则
1. **识别大型景区**：如大明湖、西湖、故宫、颐和园等
2. **景区内小景点标记**：
   - `is_scenic_inner = True`
   - `parent_scenic = "大明湖"`
3. **权重调整**：
   - 大型景区作为整体规划点位，权重高
   - 景区内小景点（如大明湖超然楼）优先级降低，不单独参与跨景区路径规划
4. **scenic_weight_factor**：大型景区权重因子，用于排序

---

### 步骤5.7：时间跨度合理性收束

**规则**
1. **按实际可支撑的区域数上限收束天数**
2. **省级目的地**：
   - `n_regions = 景点中涉及的城市数`
   - 如果 `days > n_regions`，则 `days = n_regions`
3. **市级/区级目的地**：
   - `n_regions = max(1, 聚类区数)`
   - 如果 `days > n_regions`，则 `days = n_regions`
4. **目的**：避免「规划点不足」或「过于庞杂」

#### 时间跨度归一化（意图层完成）
| 时间维度 | 收束规则 |
|---------|---------|
| **年** | 按月分配省份，哪个月是该省最佳旅行时间就安排在哪个月 |
| **月** | 1个月=本省/邻省，2个月=2省 |
| **日** | 常规逐日规划，15天上限 |

---

### 步骤5.8：LLM智能优化

**函数**：`ai_mod.optimize_itinerary(params, attrs)`

#### 策略：LLM做决策，规则做执行

1. **LLM筛选POI**：从候选景点中选择最适合的景点
2. **主题分组**：为每个景点分配主题（如"历史人文"、"自然风光"）
3. **建议时长**：为每个景点建议游览时长
4. **最佳时段**：建议上午/下午/晚上

#### 规则执行
1. **LLM选中的景点**：注入优化字段（`llm_duration`, `llm_theme`, `llm_best_slot`），优先规划
2. **不足补充**：如果LLM选中的不足 `min_needed = days * 2`，从hot景点补充
   - 排序优先级：1. 非景区内小景点优先 2. 评分高优先 3. 景区权重因子高优先
3. **总数控制**：`max_total = days * 5`

---

### 步骤5.9：大型景区与景区内小景点去重

#### 规则
1. 如果大型景区本身已被选中（如"大明湖景区"），过滤掉该景区内的小景点（如"大明湖超然楼"）
2. **双重过滤**：
   - 通过 `is_scenic_inner` 和 `parent_scenic` 匹配过滤
   - 通过名称包含匹配过滤（如"大明湖超然楼"包含"大明湖"）
3. **目的**：避免大明湖和大明湖的景点重复出现

---

### 步骤5.10：规则化地理规划

**两种规划策略**：

#### 策略A：traditional（传统）
**函数**：`_geo_plan()`

1. **地理聚类**（`cluster_attractions`）：
   - 就近优先，再向外扩散
   - 最大聚类距离 `CLUSTER_MAX_DIST`
   - 距离近的景点聚为一类

2. **贪婪分组**（`greedy_group`）：
   - 把某个点相近的优先规划，然后再往外扩
   - 每组最多3个景点，最大连接距离6000米

3. **逐日构建**（`build_days`）：
   - 按聚类分配到不同天
   - 每天景点数量根据节奏调整
   - 上午/下午/晚上时段分配

4. **跨天去重**（`dedup_landmark_day`）：
   - 同地标词去重，避免不同天重复
   - 顶级地标分组

#### 策略B：spatial_temporal（两阶段）
**函数**：`_spatial_temporal_plan()`

1. **第一阶段：空间整体路线规划**
   - 忽略时间安排
   - 按出发点 → 目的城市（多个景点） → 返程点安排所有规划
   - 总体路线优化

2. **第二阶段：按时间拆分**
   - 将整体路线按天数拆分
   - 每天的行程不重复地域
   - 住宿点作为第二天的起点

---

### 步骤5.11：天数不足补齐

**函数**：`_ensure_days()`

#### 规则
1. 候选池 = 景点 + 辅助池（美食/购物/夜生活）
2. 如果实际生成天数 < 请求天数，用规则引擎补齐
3. 从候选池中按距离、评分选择补充景点

---

### 步骤5.12：跨天地域去重

**函数**：`_enforce_region_distinct()`

#### 规则
1. 仅对非geo路径生效（geo路径已按子区域天然不重复）
2. 确保不同天的行程不在同一地域重复
3. 例：第一天杭州，第二天绍兴但包含杭州地点 → 过滤杭州地点
4. 单天的行程和后续的行程不出现地域重复

---

### 步骤5.13：POI层级数据自动挂载

**函数**：`_mount_poi_hierarchy()`

#### 三层POI数据体系
```
主POI（如"大明湖景区"）
  ├── 内部子POI（如"超然楼"、"历下亭"）
  └── 周边附属POI（如附近美食、购物）
```

#### 规则
1. 为主景点附加内部游览动线
2. 附加周边附属点位
3. 大景点内的小景点只作为点位出现，不作为规划点位

---

## 阶段6：LLM生成行程回复

**函数**：`ai_mod.generate_plan_reply(plan_dict, user_msgs)`

### 规则
1. 基于规划结果，LLM生成自然语言回复
2. 包含行程亮点、天数、点位数、预算
3. RAG人文知识融入回复
4. 品牌气质融入（"去见山海"，鼓励走出去）
5. 引导用户查看完整行程和地图

### 回复示例
```
世界在等你，北京见！✨ 已为你备好 3 天行程（人文 · 适中预算 · 适中节奏），
已安排必去：故宫、天安门、长城。共 3 天、12 个点位，预算约 ¥1500，
由内置规则引擎生成——剩下的，交给你的脚步。
点击下方按钮查看完整行程和地图～想调整随时告诉我。
```

## 关键规则汇总

### 1. 意图识别规则
- 只分析当前消息，忽略历史
- confidence < 0.7 一律返回chat
- 不确定时安全降级为chat

### 2. 行政分级枚举规则
- 省级：枚举省内城市，按市分隔
- 市/区级：1级推荐+省级补充
- 区县→市→省三级枚举

### 3. 地理聚类规则
- 就近优先，再向外扩散
- 距离近的优先规划在同一天
- 最大聚类距离限制

### 4. 跨天去重规则
- 不同天行程不重复地域
- 同地标词去重
- 跨城污染过滤（cityname）

### 5. 大型景区规则
- 大型景区作为整体规划点位
- 景区内小景点优先级降低
- 大型景区已选中时，过滤景区内小景点

### 6. 时间跨度规则
- 年：按月分配省份（最佳旅行时间）
- 月：1个月=本省/邻省，2个月=2省
- 日：常规逐日规划，15天上限
- 按可支撑区域数收束天数

### 7. 中国区域限制
- 所有规划只能规划中国区域内的地点
- 境外目的地返回错误提示

### 8. 缓存策略
- 地理编码：7天
- POI搜索：1天
- 路径规划：30分钟
- 天气：2小时
