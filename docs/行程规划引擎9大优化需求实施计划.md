## 需求1：修复主POI和子POI同时规划的问题

### 问题描述
- 大型景区（如"大明湖景区"）和景区内小景点（如"大明湖超然楼"）同时出现在行程中
- 导致重复规划，用户体验差

### 当前实现
- `is_large_scenic_area()` 识别大型景区
- `is_inside_large_scenic_area()` 识别景区内小景点
- `_mount_poi_hierarchy()` 挂载POI层级
- 在步骤5.9有去重逻辑，但可能存在漏洞

### 优化方案
1. **增强去重逻辑**：
   - 在POI检索阶段就过滤掉景区内小景点（如果大型景区存在）
   - 在行政分级枚举阶段也做同样过滤
   - 在LLM优化阶段也做同样过滤
   - 确保所有路径都生效

2. **统一去重函数**：
   - 提取 `_dedup_scenic_inner(attrs)` 统一函数
   - 在所有POI处理阶段调用
   - 日志记录去重情况

3. **POI层级展示优化**：
   - 主POI在行程中展示
   - 子POI只在主POI的详情中展示（内部游览动线）
   - 子POI不作为独立的行程节点

### 涉及文件
- `backend/app/core/planner.py` - 规划引擎
- `backend/app/services/planner/geo_enum.py` - 行政分级枚举
- `backend/app/data/static/large_scenic_areas.py` - 大型景区数据
- `backend/app/data/static/poi_hierarchy.py` - POI层级数据

## 需求2：加入景区开放时间的规划

### 问题描述
- 当前规划不考虑景区开放时间
- 可能导致规划的景点在关闭时间无法游览

### 优化方案
1. **数据层**：
   - 数据库增加 `poi_open_hours` 表
   - 字段：poi_id, day_of_week, open_time, close_time, is_closed
   - 支持特殊日期（节假日）
   - 后台可配置

2. **规则引擎**：
   - 在逐日构建时，检查每个景点的开放时间
   - 景点安排在开放时间段内
   - 如果景点周一闭馆，不安排在周一
   - 计算游览时长是否在开放时间内

3. **时间分配优化**：
   - 上午景点：开放时间早的（如公园、广场）
   - 下午景点：博物馆、纪念馆
   - 晚上景点：夜景、夜市
   - 根据开放时间自动调整时段

### 涉及文件
- `backend/app/core/planner.py` - 规划引擎
- `backend/app/services/planner/daily_build.py` - 逐日构建
- 数据库迁移脚本 - 新增poi_open_hours表
- 后台管理 - 开放时间配置页面

## 需求3：增强单个景区的内部路线规划

### 问题描述
- 当前大型景区只作为一个点位
- 景区内部的游览路线不足
- 用户不知道在景区内应该怎么逛

### 优化方案
1. **数据层**：
   - 数据库增加 `scenic_route` 表
   - 字段：scenic_id, route_name, duration, distance, poi_sequence, description
   - 每个景区支持多条路线（如经典路线、深度路线、亲子路线）
   - 后台可配置

2. **规则引擎**：
   - 当规划到大型景区时，自动推荐内部路线
   - 根据用户风格选择路线（亲子→亲子路线，人文→深度路线）
   - 根据可用时间选择路线（时间短→经典路线，时间长→深度路线）
   - 内部路线的子POI作为内部游览动线，不参与跨景区路径

3. **前端展示**：
   - 景区卡片展示推荐路线
   - 地图上展示景区内部路线（虚线）
   - 可切换不同路线

### 涉及文件
- `backend/app/core/planner.py` - 规划引擎
- `backend/app/services/planner/` - 规划服务
- 数据库迁移脚本 - 新增scenic_route表
- 前端 `DayCard.vue` - 景区卡片
- 前端 `MapView.vue` - 地图展示

## 需求4：行程和行程之间加入通行建议

### 问题描述
- 当前行程只有景点列表
- 景点之间的交通方式、时间、距离不明确
- 用户不知道怎么从A景点到B景点

### 优化方案
1. **规则引擎**：
   - 在逐日构建时，计算相邻景点之间的交通方案
   - 调用地图路径规划API（驾车、公交、步行）
   - 根据出行方式选择交通方案（自驾→驾车，公共交通→公交）
   - 计算距离、时间、费用

2. **数据结构**：
   - DayPlan.items 增加 `transport` 字段
   - transport: {mode, duration, distance, cost, description}
   - 每个景点项记录从上一个景点到当前景点的交通

3. **前端展示**：
   - 在两个景点卡片之间展示通行建议
   - 图标+文字：🚇 地铁2号线，约15分钟，2元
   - 可展开查看详细路线

### 涉及文件
- `backend/app/core/planner.py` - 规划引擎
- `backend/app/services/planner/daily_build.py` - 逐日构建
- `backend/app/services/map/route.py` - 路径规划
- 前端 `DayCard.vue` - 行程卡片
- 前端 `MapView.vue` - 地图展示

## 需求5：住宿只规划大致区域（可配置）

### 问题描述
- 当前可能推荐具体酒店
- 用户希望只推荐大致区域，不推荐具体酒店
- 需要可配置

### 优化方案
1. **后台配置**：
   - 系统配置表增加 `accommodation_mode` 配置
   - 可选值：`none`（不推荐）、`area`（只推荐区域）、`hotel`（推荐具体酒店）
   - 默认 `area`
   - 后台可修改

2. **规则引擎**：
   - 根据配置决定住宿推荐方式
   - `area`模式：推荐住宿区域（如"前门/崇文门一带"）
   - 推荐理由：交通便利、靠近景点、餐饮丰富
   - 不推荐具体酒店名称

3. **前端展示**：
   - 每天行程末尾展示住宿区域建议
   - 🏨 建议住在：前门/崇文门一带（地铁2号线/8号线交汇，步行可达天安门）

### 涉及文件
- `backend/app/core/planner.py` - 规划引擎
- `backend/app/data/dict_store.py` - 字典/配置存储
- 后台管理 - 系统配置页面
- 前端 `DayCard.vue` - 行程卡片

## 需求6：最后一天规划考虑返程车站附近

### 问题描述
- 当前规划不考虑返程
- 最后一天可能规划离车站很远的景点
- 导致赶车紧张

### 优化方案
1. **参数扩展**：
   - PlanRequest 增加 `return_station` 字段（返程车站）
   - 支持火车站、机场、汽车站
   - 从用户对话中提取（如"下午3点的高铁"）

2. **规则引擎**：
   - 最后一天的景点优先规划在返程车站附近
   - 计算最后一个景点到车站的时间
   - 预留足够的赶车时间（高铁提前1小时，飞机提前2小时）
   - 如果时间紧张，减少最后一天的景点数量
   - 最后一个景点离车站不超过30分钟车程

3. **去程考虑**：
   - 第一天的景点优先规划在到达车站附近
   - 根据到达时间调整第一天行程

### 涉及文件
- `backend/app/core/planner.py` - 规划引擎
- `backend/app/ai/ai.py` - 意图识别（提取车站信息）
- `backend/app/services/map/route.py` - 路径规划
- 前端 - 行程展示

## 需求7：前端只有景点再有AI介绍

### 问题描述
- 当前可能所有点位都有AI介绍
- 用户希望只有景点才有AI介绍
- 美食、购物、夜生活不需要AI介绍

### 优化方案
1. **前端判断**：
   - 在DayCard中判断POI类型
   - 只有 `category == "景点"` 或 `type == "风景名胜"` 才展示AI介绍
   - 其他类型只展示基本信息（名称、地址、评分）

2. **数据结构**：
   - POI增加 `ai_intro` 字段（AI生成的介绍）
   - 只在景点类型的POI中填充
   - 其他类型为空

### 涉及文件
- 前端 `DayCard.vue` - 行程卡片
- 前端 `POICard.vue` - POI卡片
- `backend/app/core/planner.py` - 规划引擎

## 需求8：后台增加知识检索和介绍的配置管理（B端）

### 问题描述
- 当前RAG知识库是静态的
- B端用户希望能灵活配置知识内容
- 人为干预知识检索和介绍

### 优化方案
1. **数据库设计**：
   - `knowledge_base` 表：知识库分类（景点人文、历史名人、美食文化、旅行贴士）
   - `knowledge_doc` 表：知识文档（标题、内容、来源、标签、关联POI、状态）
   - `knowledge_poi_mapping` 表：知识与POI的关联
   - 支持草稿、发布、下架状态

2. **后台管理页面**：
   - 知识库列表：分类、文档数、状态
   - 文档编辑：富文本编辑器、标签、关联POI
   - 检索测试：输入关键词，测试检索结果
   - 人工干预：置顶、屏蔽、调整权重

3. **RAG服务优化**：
   - 优先检索已发布的知识库文档
   - 支持按分类检索
   - 支持人工置顶的文档优先
   - 支持屏蔽某些文档

4. **B端灵活配置**：
   - 可配置是否启用RAG
   - 可配置检索结果数量
   - 可配置是否允许AI生成补充内容
   - 可配置知识更新频率

### 涉及文件
- 数据库迁移脚本 - 新增knowledge相关表
- 后台 `RagPanel.vue` - 知识库管理页面
- `backend/app/api/rag.py` - RAG API
- `backend/app/services/rag/` - RAG服务

## 需求9：加入语音介绍（TTS），内容更详尽

### 问题描述
- 当前只有文字介绍
- 用户希望有语音介绍
- 语音内容要更详尽

### 优化方案
1. **TTS服务**：
   - 后端集成TTS API（如百度TTS、腾讯TTS、或本地TTS模型）
   - 支持中文语音合成
   - 支持多种音色（男声、女声、童声）
   - 支持语速、语调调整

2. **语音内容生成**：
   - 景点语音介绍比文字更详尽
   - 包含：景点历史、文化背景、著名典故、游览建议、拍照机位
   - 时长约1-3分钟
   - LLM生成语音脚本，然后TTS合成

3. **前端展示**：
   - 景点卡片增加播放按钮
   - 点击播放语音介绍
   - 显示播放进度、时长
   - 支持暂停、继续、停止
   - 支持后台播放

4. **缓存策略**：
   - 语音文件缓存到本地或CDN
   - 相同景点不重复生成
   - 支持预加载（行程页面加载时预加载当前天的语音）

### 涉及文件
- `backend/app/services/tts/` - TTS服务（新增）
- `backend/app/api/tts.py` - TTS API（新增）
- `backend/app/ai/ai.py` - 语音脚本生成
- 前端 `POICard.vue` - 语音播放组件
- 前端 `audioPlayer.js` - 音频播放器工具

## 风险与注意事项

1. **POI去重**：确保所有路径都生效，避免漏洞
2. **开放时间数据**：数据量较大，需要后台批量导入
3. **景区内部路线**：需要人工配置，数据准备工作量大
4. **通行建议**：增加地图API调用，注意配额和缓存
5. **TTS服务**：需要第三方API，注意费用和配额
6. **知识库管理**：需要富文本编辑器，前端工作量较大
