# 行程规划引擎完整流程与规则体系

> 文档版本：v1.1  
> 更新时间：2026-08-29  
> 适用范围：行程规划引擎的完整流程设计，从参数识别到最终输出的9个阶段

---

## 1. 文档概述

本文档详细设计行程规划引擎的完整流程，解决以下关键问题：

1. **规划行程的完整流程是什么**：从用户输入到最终输出，经历哪些阶段
2. **每个阶段的规则是什么**：每个阶段的输入、输出、核心规则、关键算法
3. **阶段之间的衔接关系**：前一阶段的输出如何作为后一阶段的输入
4. **规则体系的完整性**：确保每个阶段都有明确的规则，不遗漏关键环节

**核心观点**：参数识别只是规划的第一阶段，完整的规划流程包含9个阶段，每个阶段都有明确的规则和算法。

---

## 2. 规划流程总览

### 2.1 九阶段流程

```
用户输入
    ↓
【阶段1】参数识别（LLM解析）
    ↓ 规划参数（destination, days, travelers, group_type, budget_level, style, pace, traffic_mode...）
【阶段2】景点检索与筛选
    ↓ 候选景点池（筛选后的景点列表）
【阶段3】景点聚类与分组
    ↓ 景点聚类（按地理距离/行政区域/类型分组）
【阶段4】按天分配与切分
    ↓ 每日景点（每天分配的景点列表）
【阶段5】每日排序与时间线
    ↓ 时间线行程（每天内景点顺序+时间段）
【阶段6】辅助点位与通行建议
    ↓ 完整行程（景点+美食+购物+夜生活+通行建议）
【阶段7】预算计算与优化
    ↓ 带预算行程（餐饮+住宿+交通+门票+总预算）
【阶段8】LLM优化与文案生成
    ↓ 优化后行程（智能优化+人文介绍+出发语+每日灵感）
【阶段9】验证与输出
    ↓
最终行程输出
```

### 2.2 各阶段核心职责

| 阶段 | 名称 | 核心职责 | 输入 | 输出 |
|------|------|----------|------|------|
| 1 | 参数识别 | LLM解析用户输入，提取规划参数 | 用户对话 | 规划参数对象 |
| 2 | 景点检索与筛选 | 检索候选景点，按参数筛选 | 规划参数 | 候选景点池 |
| 3 | 景点聚类与分组 | 按地理距离/行政区域/类型聚类 | 候选景点池 | 景点聚类 |
| 4 | 按天分配与切分 | 将聚类分配到每天，跨天去重 | 景点聚类 | 每日景点 |
| 5 | 每日排序与时间线 | 每天内景点排序，应用时间线 | 每日景点 | 时间线行程 |
| 6 | 辅助点位与通行建议 | 添加美食/购物/夜生活，通行建议 | 时间线行程 | 完整行程 |
| 7 | 预算计算与优化 | 计算各项预算，优化调整 | 完整行程 | 带预算行程 |
| 8 | LLM优化与文案生成 | LLM智能优化，生成文案和人文介绍 | 带预算行程 | 优化后行程 |
| 9 | 验证与输出 | 验证行程合理性，格式化输出 | 优化后行程 | 最终行程 |

## 3. 阶段1：参数识别

### 3.1 阶段概述

**核心职责**：使用LLM解析用户输入，提取规划所需的各项参数。

**输入**：用户对话（可能包含多轮对话历史）

**输出**：规划参数对象（PlanRequest）

### 3.2 识别参数清单

| 参数名 | 含义 | 是否必须 | 默认值 | 取值范围 |
|--------|------|----------|--------|----------|
| destination | 目的地 | 是 | 无 | 全国/省/市/区县/具体地点 |
| days | 出行天数 | 否 | 3 | 1-15天 |
| origin | 出发点 | 否 | 空 | 具体地点 |
| travelers | 出行人数 | 否 | 1 | 1-99人 |
| return_point | 返回点 | 否 | 空 | 具体地点 |
| group_type | 人群类型 | 否 | 单人 | 单人/情侣/亲子/家庭/朋友/老人 |
| budget_level | 预算档位 | 否 | 适中 | 经济/适中/舒适/奢华 |
| style | 旅行风格 | 否 | 美食+人文 | 美食/人文/网红/小众/亲子/自然 |
| pace | 节奏 | 否 | 适中 | 轻松/适中/暴走 |
| traffic_mode | 出行方式 | 否 | 公共交通 | 自驾/公共交通/骑行/步行/混合 |
| must_include_poi | 必去景点 | 否 | 空 | 景点名称数组 |
| exclude_poi | 排除景点 | 否 | 空 | 景点名称数组 |
| interests | 兴趣标签 | 否 | 空 | 兴趣标签数组 |

### 3.3 核心规则

1. **目的地必须识别**：如果无法识别目的地，回复用户询问目的地
2. **参数兜底**：未识别的参数使用默认值
3. **参数收束**：超过范围的参数收束到合理范围
4. **上下文继承**：多轮对话中，后续对话继承已识别的参数
5. **参数更新**：用户明确修改的参数更新，其他参数保持不变

### 3.4 详细规则

详见《规划引擎核心规则体系设计》文档第2章（无上限参数的兜底和收束规则）、第3章（人群参数对出行规划的影响点）、第4章（出行方式的影响规则及灵活机制）。

## 4. 阶段2：景点检索与筛选

### 4.1 阶段概述

**核心职责**：对目的地做同名处理，然后行政分级枚举，POI检索，最后按照人群筛选景点。

**输入**：规划参数对象（PlanRequest）

**输出**：候选景点池（筛选后的景点列表）

**规则执行顺序**：
1. 目的地同名地点处理
2. 行政分级枚举
3. POI检索
4. 按照人群筛选

> **注意**：主/子POI识别移到阶段3（景点聚类与分组）进行。

### 4.2 目的地同名地点处理（第一步）

#### 4.2.1 地名重复处理

1. **优先以目的地的地点为先**：如果存在同名地点，优先选择与用户输入目的地行政区域一致的地点
2. **通过用户对话确认**：如果无法确定，通过用户对话确认具体是哪个地点
3. **避免地点飘逸**：确保地点定位准确，不漂移到其他同名地点

#### 4.2.2 景点名重复处理

1. **优先以目的地所在行政区域的景点为先**：如果存在同名景点，优先选择目的地所在行政区域的景点
2. **通过用户对话确认**：如果无法确定，通过用户对话确认具体是哪个景点
3. **避免景点飘逸**：确保景点定位准确，不漂移到其他同名景点

#### 4.2.3 处理流程

```
用户输入目的地
    ↓
是否存在同名地点？
    ├─ 否 → 直接使用
    └─ 是 → 优先选择与用户输入行政区域一致的地点
        ↓
        是否能确定？
        ├─ 是 → 使用确定的地点
        └─ 否 → 通过用户对话确认
            ↓
            使用用户确认的地点
```

### 4.3 行政分级枚举（第二步）

#### 4.3.1 行政分级枚举规则

根据目的地的行政等级，分级枚举景点：

| 目的地等级 | 检索范围 | 优先级 |
|------------|----------|--------|
| **省级** | 枚举省内各市的景点 | 按市分隔，每个市的景点作为一组 |
| **市级/区级/地点级** | 先把当前市级/区级/地点作为1级推荐，再往上枚举至省下的地点作为补充 | 1级推荐优先，补充景点次之 |

### 4.4 POI检索（第三步）

#### 4.4.1 检索来源

1. **本地行政区域数据**：优先从本地行政区域数据中检索
2. **高德/腾讯POI搜索**：本地数据不足时，调用第三方API检索
3. **必打卡地标库**：从数据库中读取必去地标，强制注入

#### 4.4.2 检索类别

| 类别 | 说明 | 是否主规划 |
|------|------|------------|
| **景点** | 风景名胜、历史古迹、公园、博物馆等 | 是（主规划） |
| **美食** | 餐厅、小吃、美食街等 | 否（辅助） |
| **购物** | 商场、商业街、市场等 | 否（辅助） |
| **夜生活** | 酒吧、夜市、夜景等 | 否（辅助） |

**核心规则**：景点作为主规划路径，美食、购物、夜生活只做辅助，不参与主规划路径。

### 4.5 按照人群筛选（第四步）

#### 4.5.1 按人群筛选

| 人群类型 | 筛选规则 | 保留比例 |
|----------|----------|----------|
| **单人** | 不特别筛选，保留所有景点 | 90%主要景点 + 10%小众/个性化 |
| **情侣** | 增加浪漫/网红景点，保留主要景点 | 80%主要景点 + 20%浪漫/网红 |
| **亲子** | 筛选亲子友好景点，增加亲子/游乐园 | 60%亲子友好名胜 + 40%亲子/游乐园 |
| **家庭** | 筛选全家友好景点，保留主要景点 | 85%主要景点 + 15%全家友好 |
| **朋友** | 增加网红/夜生活/美食景点，保留主要景点 | 70%主要景点 + 30%网红/夜生活/美食 |
| **老人** | 筛选平缓/文化景点，保留主要景点 | 90%主要景点 + 10%平缓/文化 |

#### 4.3.2 按风格筛选

| 旅行风格 | 筛选规则 |
|----------|----------|
| **美食** | 优先选择美食街、特色餐厅附近的景点 |
| **人文** | 优先选择博物馆、历史遗迹、文化景点 |
| **网红** | 优先选择网红打卡点、热门景点 |
| **小众** | 优先选择小众景点、冷门景点 |
| **亲子** | 优先选择亲子友好、游乐园、动物园 |
| **自然** | 优先选择自然风光、公园、山川湖海 |

#### 4.3.3 按预算筛选

| 预算档位 | 筛选规则 |
|----------|----------|
| **经济** | 优先选择免费/低价景点 |
| **适中** | 综合考虑，包括收费景点 |
| **舒适** | 优先选择高品质景点、VIP体验 |
| **奢华** | 优先选择顶级景点、私人定制体验 |

#### 4.3.4 硬性约束筛选

1. **必去景点**：must_include_poi中的景点必须保留
2. **排除景点**：exclude_poi中的景点必须过滤
3. **中国区域校验**：仅保留中国境内的景点
4. **开放状态校验**：过滤已关闭、停业、拆迁的景点

### 4.6 本阶段输出

候选景点池，包含以下信息：
- 景点名称、类型、经纬度、行政区域
- 评分、权重
- 建议游玩时长、开放时间
- 门票价格
- 人群标签、风格标签
- 景点强度（高强度/中强度/低强度）

> **注意**：主/子POI识别在阶段3（景点聚类与分组）进行，本阶段不做主/子POI识别。

## 5. 阶段3：景点聚类与分组

### 5.1 阶段概述

**核心职责**：首先做主/子POI的识别规划，然后将候选景点池中的景点，按地理距离、行政区域、景点类型进行聚类和分组。

**输入**：候选景点池

**输出**：景点聚类（多个景点组，每组包含地理位置相近的景点）

**规则执行顺序**：
1. 主/子POI的识别规划
2. 景点的分组
3. 按照地理距离的规划

### 5.2 主/子POI识别规划（第一步）

#### 5.2.1 大型景区识别

从大型景区库中识别大型景区（如故宫、西湖、大明湖），大型景区作为主POI。

#### 5.2.2 子POI标记

大型景区内的小景点作为子POI（如故宫内的太和殿、乾清宫）。

#### 5.2.3 权重调整

- 主POI：权重高，优先规划
- 子POI：权重降低，作为主POI的补充，不单独作为规划点位

#### 5.2.4 去重逻辑

- 如果主POI已经在行程中，子POI只作为点位介绍，不单独规划
- 如果主POI不在行程中，子POI可以单独规划，但优先级降低

#### 5.2.5 聚类中的主/子POI处理

- 主POI作为聚类的核心，子POI依附于主POI所在的聚类
- 子POI不单独成组，而是作为主POI的内部点位
- 聚类时只考虑主POI和独立景点的地理距离，子POI不参与聚类

### 5.3 聚类目标

1. **地理就近**：地理位置相近的景点聚为一组
2. **行政区域一致**：同一行政区域的景点优先聚为一组
3. **景点类型协调**：同一组内景点类型协调（避免全是博物馆或全是公园）
4. **组数合理**：聚类数量与出行天数匹配（通常组数 = 天数或略多于天数）

### 5.3 聚类算法

#### 5.3.1 基于地理距离的聚类

1. **计算距离矩阵**：计算所有景点之间的地理距离
2. **贪心聚类**：
   - 从评分最高的景点开始
   - 将距离最近的景点加入同一组
   - 直到组内景点数量达到上限（通常每天3-5个）
   - 然后开始下一组
3. **圈层分配**：
   - 以目的地中心为圆心
   - 按距离划分为多个圈层（如0-3公里、3-10公里、10公里以上）
   - 每个圈层的景点聚为一组或多组

#### 5.3.2 基于行政区域的聚类

1. **按区县分组**：同一区县的景点优先聚为一组
2. **按市分组**：跨市行程中，同一市的景点聚为一组
3. **跨城污染过滤**：避免同一组内包含不同城市的景点（除非是跨城日）

#### 5.3.3 基于景点类型的聚类

1. **类型协调**：同一组内景点类型多样化（人文+自然+美食）
2. **顶级地标分组**：顶级地标（如故宫、长城）单独成组或作为组的核心
3. **同地标词去重**：同一地标词的景点（如"天安门广场"和"天安门城楼"）优先聚为一组

### 5.4 聚类数量控制

| 出行天数 | 聚类数量 | 说明 |
|----------|----------|------|
| 1天 | 1组 | 单日行程 |
| 2-3天 | 2-3组 | 每组对应1天 |
| 4-7天 | 4-7组 | 每组对应1天，可能有跨城组 |
| 8-15天 | 8-15组 | 每组对应1天，跨城/跨省组 |

### 5.5 本阶段输出

景点聚类，包含以下信息：
- 聚类ID、聚类名称（如"市中心经典组"、"郊区自然风光组"）
- 组内景点列表
- 聚类中心经纬度
- 聚类覆盖的行政区域
- 聚类评分（组内景点平均评分）

## 6. 阶段4：按天分配与切分

### 6.1 阶段概述

**核心职责**：将景点聚类分配到每天，考虑跨天区域去重、时间跨度收束、住宿点等因素。

**输入**：景点聚类

**输出**：每日景点（每天分配的景点列表）

### 6.2 分配策略

#### 6.2.1 基于旅行体验曲线的分配（核心策略）

**人的旅行体验曲线**：
```
第1天：兴奋但疲劳（长途旅行后）→ 轻松入门
第2-3天：体力充沛、兴趣最高 → 核心景点
第4-5天：体力开始下降 → 中等强度
第6天+：疲劳累积 → 轻松收尾
```

**分配规则**：

| 天数 | 体验状态 | 分配策略 | 景点类型 |
|------|----------|----------|----------|
| **第1天** | 兴奋但疲劳 | 轻松入门，安排市中心/交通便利的景点 | 低强度：博物馆、公园、街区 |
| **第2-3天** | 体力充沛 | 核心景点，安排最重要、最耗体力的景点 | 高强度：长城、爬山、大型景区 |
| **第4-5天** | 体力下降 | 中等强度，安排次重要景点 | 中强度：历史古迹、文化景点 |
| **第6天+** | 疲劳累积 | 轻松收尾，安排返程车站附近景点 | 低强度：购物、休闲、美食 |

**示例（北京5天）**：
- 第1天：天安门广场 + 故宫（市中心，交通便利，中等强度）
- 第2天：慕田峪长城（高强度，核心景点，体力充沛时安排）
- 第3天：颐和园 + 圆明园（中高强度，皇家园林）
- 第4天：天坛 + 前门大街（中等强度，文化+购物）
- 第5天：奥林匹克公园 + 返程（低强度，靠近车站，轻松收尾）

#### 6.2.2 基于体力曲线的分配

**体力交替原则**：避免连续安排高强度景点，高强度和低强度交替。

| 景点强度 | 说明 | 示例 |
|----------|------|------|
| **高强度** | 需要大量步行、爬山、耗时久 | 长城、泰山、黄山、大型景区 |
| **中强度** | 中等步行、耗时中等 | 故宫、颐和园、兵马俑 |
| **低强度** | 少量步行、耗时短、可休息 | 博物馆、公园、街区、购物 |

**分配规则**：
- 高强度景点后必须安排低强度景点（休息恢复）
- 最多连续2天中等强度
- 每周最多1-2个高强度景点

**错误示例**：
- 第1天：长城（高强度）
- 第2天：泰山（高强度）← 错误，连续高强度，体力透支

**正确示例**：
- 第1天：长城（高强度）
- 第2天：博物馆+公园（低强度）← 正确，休息恢复
- 第3天：颐和园（中强度）

#### 6.2.3 基于景点热度的分配

**工作日 vs 周末**：
- 热门景点安排在工作日（避免周末人流高峰）
- 冷门景点可以安排在周末

**室内 vs 室外**：
- 室外景点安排在天气好的日子
- 室内景点可以安排在天气不好的日子（如下雨）

**早开 vs 晚开**：
- 早开景点（如故宫8:30开门）安排在上午
- 晚开景点（如商场10:00开门）安排在下午

#### 6.2.4 基于住宿区域的分配

**住宿连续性原则**：
- 同一住宿区域的景点安排在连续的几天
- 避免频繁更换住宿区域（每2-3天换一次住宿比较合理）

**分配规则**：
- 第1-2天：住宿在A区域，安排A区域附近景点
- 第3-4天：住宿在B区域，安排B区域附近景点
- 第5天：住宿在C区域（靠近车站），安排C区域附近景点

#### 6.2.5 传统策略（traditional）

1. **按聚类评分排序**：评分高的聚类优先分配
2. **按天顺序分配**：第1天分配评分最高的聚类，第2天分配次高的，以此类推
3. **每天景点数量控制**：根据节奏配置（轻松3个/适中4个/暴走5个）
4. **跨天区域去重**：避免同一区县景点跨天重复

#### 6.2.6 两阶段策略（spatial_temporal）

1. **先空间整体规划**：规划出发点 → 目的城市（多个景点） → 返回点的整体路线
2. **再按时间拆分**：将整体路线按时间拆分为每天
3. **考虑出发点和返回点**：第1天从出发点附近开始，最后一天在返回点附近结束

### 6.3 跨天区域去重规则

1. **按区县去重**：同一区县的景点尽量安排在同一天
2. **按市去重**：跨市行程中，同一市的景点尽量安排在连续的几天
3. **避免区域重复**：如第1天在杭州，第2天在绍兴，第2天的行程不应包含杭州的地点

### 6.4 时间跨度收束规则

1. **按可支撑区域数收束**：如果目的地可支撑的区域数 < 天数，收束天数
2. **大时间跨度处理**：
   - 月度：1个月规划当前省或临近省，2个月安排2个省
   - 年度：按省规划，哪个月是这个省的最佳出行时间就安排在哪个月

### 6.5 住宿点考虑规则

1. **住宿点作为第二天起点**：如果规划了住宿，住宿点作为第二天的起点
2. **住宿区域推荐**：
   - 只推荐大致区域，不推荐具体酒店（可配置）
   - 推荐交通便利、景点集中的区域
3. **最后一天住宿**：最后一天住宿考虑返程车站附近

### 6.6 返程车站考虑规则

如果用户提供了返程车站信息：

1. **最后一天景点安排**：最后一天景点安排在返程车站附近
2. **时间倒推**：根据返程出发时间，倒推最后一天的行程安排
3. **交通时间预留**：预留从最后一个景点到车站的交通时间

### 6.7 本阶段输出

每日景点，包含以下信息：
- 第几天、日期
- 当天景点列表（按顺序）
- 当天主题（如"中轴线经典"、"皇家园林"）
- 住宿推荐区域
- 当天总游玩时长预估

## 7. 阶段5：每日排序与时间线

### 7.1 阶段概述

**核心职责**：对每天内的景点进行排序，然后应用时间线（上午/中午/下午/晚上），考虑开放时间、建议游玩时长等因素。

**输入**：每日景点

**输出**：时间线行程（每天内景点顺序+时间段）

### 7.2 每日排序规则

#### 7.2.1 基于人流高峰的排序（核心策略）

**避开人流高峰原则**：

| 景点类型 | 人流高峰 | 最佳游览时间 |
|----------|----------|--------------|
| **热门景点**（故宫、长城） | 10:00-15:00 | 开门时（8:30-10:00）或闭馆前（15:00-17:00） |
| **室外景点** | 12:00-14:00（高温） | 上午（09:00-12:00）或傍晚（16:00-18:00） |
| **室内景点**（博物馆） | 14:00-16:00 | 上午（09:00-12:00）或闭馆前 |
| **购物/商场** | 14:00-18:00 | 晚上（18:00-21:00） |
| **夜景** | 19:00-21:00 | 日落后（19:00-21:00） |

**排序规则**：
- 热门景点安排在开门时或闭馆前
- 室外景点安排在上午（避开下午高温）
- 室内景点可以安排在下午
- 购物安排在晚上
- 夜景安排在日落后

#### 7.2.2 基于光照和拍照的排序

**顺光原则**：

| 景点朝向 | 最佳拍照时间 | 说明 |
|----------|--------------|------|
| **朝东** | 上午（09:00-11:00） | 顺光，光线柔和 |
| **朝南** | 上午或下午 | 全天光线都不错 |
| **朝西** | 下午（15:00-17:00） | 顺光，夕阳很美 |
| **朝北** | 中午（11:00-13:00） | 避免阴影 |
| **全景/俯瞰** | 傍晚（17:00-19:00） | 夕阳+夜景过渡 |

**排序规则**：
- 朝东的景点安排在上午
- 朝西的景点安排在下午
- 全景/俯瞰景点安排在傍晚
- 夜景景点安排在日落后

**示例（北京）**：
- 上午：故宫（朝南，上午光线好）
- 下午：景山公园（俯瞰故宫，下午顺光）
- 傍晚：什刹海（夕阳+夜景）
- 晚上：南锣鼓巷（夜景+美食）

#### 7.2.3 基于用餐的排序

**用餐便利性原则**：

| 用餐时间 | 排序规则 |
|----------|----------|
| **午餐（12:00-13:30）** | 上午最后一个景点结束在美食街/餐厅集中区域附近 |
| **晚餐（18:00-19:30）** | 下午最后一个景点结束在晚餐区域/夜生活区域附近 |
| **早餐（08:00-09:00）** | 住宿附近，或第一个景点附近 |

**排序规则**：
- 上午景点结束在美食街附近（方便午餐）
- 下午景点结束在晚餐区域附近
- 避免景点和餐厅距离过远（步行不超过10分钟）

#### 7.2.4 基于地理距离的排序

1. **贪心最近邻**：从第一个景点开始，每次选择距离最近的下一个景点
2. **路线优化**：避免来回折返，尽量形成环形或单向路线
3. **起点和终点**：
   - 第1天起点考虑出发点/住宿点
   - 最后一天终点考虑返回点/返程车站

#### 7.2.5 基于开放时间的精确排序

**精确计算原则**：

| 时间要素 | 说明 |
|----------|------|
| **开门时间** | 景点最早可以进入的时间 |
| **最后入场时间** | 景点最晚可以进入的时间（通常闭馆前1小时） |
| **闭馆时间** | 景点关闭时间 |
| **建议游玩时长** | 游览该景点需要的时间 |
| **每周闭馆日** | 如故宫周一闭馆 |

**排序规则**：
- 只在开放时间内安排景点
- 考虑最后入场时间（如故宫16:00停止入场，17:00闭馆）
- 每周闭馆日不安排该景点
- 精确计算游玩时长，不超时

#### 7.2.6 基于交通时间的精确排序

**交通时间精确计算**：

| 交通要素 | 说明 |
|----------|------|
| **景点间交通时间** | 从A景点到B景点需要的时间 |
| **交通高峰时段** | 如早高峰7:30-9:30，晚高峰17:00-19:00 |
| **缓冲时间** | 预留的额外时间（如找入口、排队、上厕所） |

**排序规则**：
- 精确计算景点之间的交通时间
- 考虑交通高峰时段（高峰时段交通时间增加50%）
- 每个景点之间预留15-30分钟缓冲时间
- 避免在交通高峰时段安排长距离移动

#### 7.2.7 基于主/子POI的排序

**大型景区内部排序**：

对于大型景区（如故宫、西湖），需要规划景区内部的游览路线：

| 排序要素 | 说明 |
|----------|------|
| **入口和出口** | 确定最佳入口和出口（如故宫午门进、神武门出） |
| **内部景点顺序** | 规划景区内小景点的游览顺序（如故宫中轴线：午门→太和殿→中和殿→保和殿→乾清宫→坤宁宫→御花园→神武门） |
| **代步工具** | 推荐缆车、游船、观光车等代步工具 |
| **最佳拍照点** | 推荐景区内的最佳拍照点 |
| **休息点** | 推荐景区内的休息点（如长椅、咖啡馆、餐厅） |

**排序规则**：
- 主POI（大型景区）作为一个整体安排在时间段内
- 子POI（景区内小景点）只作为点位介绍，不单独占用时间段
- 规划景区内部的游览路线，作为主POI的详细说明

#### 7.2.8 基于景点类型的排序

1. **人文景点优先上午**：博物馆、历史遗迹等需要精力的景点安排在上午
2. **自然景点优先下午**：公园、自然风光等可以安排在下午
3. **夜景/夜生活安排晚上**：夜景、夜市、酒吧等安排在晚上
4. **购物安排下午或晚上**：商场、商业街等安排在下午或晚上

### 7.3 时间线应用规则

#### 7.3.1 时段划分

| 时段 | 时间范围 | 安排内容 |
|------|----------|----------|
| **上午** | 09:00-12:00 | 主要景点（人文/历史/大景点） |
| **中午** | 12:00-14:00 | 午餐 + 休息 |
| **下午** | 14:00-18:00 | 次要景点（自然/公园/购物） |
| **晚上** | 18:00-21:00 | 晚餐 + 夜景/夜生活 |

#### 7.3.2 每日出发和结束时间

- 默认每日出发时间：09:00
- 默认每日结束时间：21:00
- 用户可以自定义daily_start_time和daily_end_time

#### 7.3.3 节奏与景点数量

| 节奏 | 每天景点数量 | 时间安排特点 |
|------|--------------|--------------|
| **轻松** | 3个 | 每个景点游玩时间长，中间休息时间多 |
| **适中** | 4个 | 平衡游玩和休息 |
| **暴走** | 5个 | 每个景点游玩时间短，尽量多游览 |

### 7.4 单个景区内部路线规划

对于大型景区（如故宫、西湖），需要规划景区内部的游览路线：

1. **入口和出口**：确定最佳入口和出口（如故宫午门进、神武门出）
2. **内部景点顺序**：规划景区内小景点的游览顺序
3. **代步工具**：推荐缆车、游船、观光车等代步工具
4. **最佳拍照点**：推荐景区内的最佳拍照点

### 7.5 本阶段输出

时间线行程，包含以下信息：
- 第几天、日期
- 时间段（上午/中午/下午/晚上）
- 每个时间段的景点/活动
- 每个景点的建议游玩时长
- 每个景点的开放时间
- 用餐时间和推荐餐厅类型

## 8. 阶段6：辅助点位与通行建议（含检视与补充）

### 8.1 阶段概述

**核心职责**：在主行程基础上，添加美食、购物、夜生活等辅助点位，并提供景点间通行方式建议。**规划完成后检视整体行程是否符合要求，不符合要求从候选景点池没入选和辅助点位中挑选穿插进去，后续暂不更改。**

**输入**：时间线行程

**输出**：完整行程（景点+美食+购物+夜生活+通行建议）

**规则执行顺序**：
1. 辅助点位推荐（美食、购物、夜生活）
2. 通行建议
3. 规划完成后检视整体行程
4. 不符合要求从候选景点池没入选和辅助点位中挑选穿插进去
5. 后续暂不更改（阶段7、8、9不更改景点安排）

### 8.2 辅助点位推荐规则

#### 8.2.1 美食推荐

1. **用餐时间**：午餐（12:00-13:30）和晚餐（18:00-19:30）
2. **推荐位置**：景点附近，步行可达
3. **按人群推荐**：
   - 亲子：亲子餐厅、有儿童餐的餐厅
   - 老人：清淡、软烂、易消化的餐厅
   - 情侣：浪漫餐厅、景观餐厅
   - 朋友：网红餐厅、特色小吃、夜市
4. **按预算推荐**：
   - 经济：小吃、快餐、平价餐厅
   - 适中：中档餐厅、特色餐厅
   - 舒适：高档餐厅、网红餐厅
   - 奢华：米其林餐厅、顶级餐厅

#### 8.2.2 购物推荐

1. **推荐时间**：下午或晚上
2. **推荐位置**：景点附近或行程终点
3. **按人群推荐**：
   - 亲子：儿童用品店、玩具店
   - 情侣：精品店、首饰店
   - 朋友：潮牌店、买手店
4. **按风格推荐**：
   - 网红：网红商场、快闪店
   - 小众：独立设计师店、古着店
   - 人文：书店、文创店

#### 8.2.3 夜生活推荐

1. **推荐时间**：晚上（19:00以后）
2. **推荐位置**：住宿附近或行程终点
3. **按人群推荐**：
   - 亲子：不推荐夜生活，推荐夜景
   - 老人：推荐夜景，不推荐酒吧
   - 情侣：浪漫酒吧、夜景漫步
   - 朋友：酒吧、夜市、KTV
4. **按风格推荐**：
   - 网红：网红酒吧、夜景打卡点
   - 小众：独立酒吧、livehouse
   - 人文：夜景、文化街区

#### 8.2.4 辅助点位不参与跨天去重

美食、购物、夜生活只做辅助，不参与主规划路径的跨天去重，可以重复出现。

### 8.3 通行建议规则

#### 8.3.1 规划程度判断

根据场景判断出行方式规划进行程的程度（详细规划/简要规划/不规划）。

详见《规划引擎核心规则体系设计》文档第4.8节（出行方式规划进行程的程度分级）。

#### 8.3.2 景点间通行方式选择

根据距离、人群、预算、特殊场景选择通行方式：

| 景点间距离 | 推荐通行方式 |
|------------|--------------|
| <500米 | 步行 |
| 500米-2公里 | 共享单车 |
| 2-5公里 | 打车/地铁 |
| 5-15公里 | 地铁/打车 |
| 15-30公里 | 地铁/打车/自驾 |
| >30公里 | 自驾/高铁 |

#### 8.3.3 详细规划的内容

如果是详细规划，提供：
1. **交通方式**：明确标注步行/骑行/地铁/公交/打车/自驾等
2. **时间预估**：预估交通所需时间
3. **费用预估**：预估交通费用
4. **换乘提示**：如果需要换乘，标注换乘站点和线路
5. **注意事项**：特殊提示

#### 8.3.4 简要规划的内容

如果是简要规划，仅提供：
1. **交通方式建议**：推荐1-2种交通方式
2. **不标注时间和费用**

#### 8.3.5 不规划

如果是不规划，完全不体现交通方式。

### 8.4 规划完成后的检视与补充规则

#### 8.4.1 检视维度

规划完成后，从以下维度检视整体行程是否符合要求：

| 检视维度 | 检视内容 | 合格标准 |
|----------|----------|----------|
| **景点数量** | 每天景点数量是否符合节奏配置 | 轻松3个/适中4个/暴走5个 |
| **景点质量** | 是否包含必去景点、顶级地标 | 必去景点全部包含 |
| **人群匹配** | 景点是否符合人群类型 | 亲子/老人景点占比符合要求 |
| **时间合理** | 每天时间安排是否合理 | 不超时、不冲突、有休息 |
| **交通合理** | 景点间交通时间是否合理 | 不超过2小时/次 |
| **预算合理** | 总预算是否在预算档位范围内 | 上下浮动不超过20% |
| **跨天去重** | 不同天景点是否跨区域重复 | 同一区县不跨天重复 |
| **强度合理** | 高强度景点是否连续安排 | 高强度后有低强度休息 |

#### 8.4.2 不符合要求的补充规则

**补充来源**：
1. **候选景点池没入选的景点**：从阶段2筛选后但没入选的景点中挑选
2. **辅助点位**：从美食、购物、夜生活等辅助点位中挑选

**补充场景**：

| 不符合场景 | 补充策略 | 补充来源 |
|------------|----------|----------|
| **景点数量不足** | 增加景点 | 候选景点池没入选的景点 |
| **缺少必去景点** | 插入必去景点 | 候选景点池没入选的景点 |
| **人群匹配不足** | 增加人群相关景点 | 候选景点池没入选的景点 |
| **时间有空隙** | 插入辅助点位 | 美食、购物、夜生活 |
| **强度过高** | 替换为低强度景点 | 候选景点池没入选的低强度景点 |
| **跨天重复** | 替换为其他区域景点 | 候选景点池没入选的其他区域景点 |

**补充规则**：
- 优先从候选景点池没入选的景点中挑选（保证景点质量）
- 辅助点位（美食、购物、夜生活）只作为时间空隙的补充
- 补充后重新检视，直到符合要求
- **后续暂不更改**（阶段7、8、9不更改景点安排）

#### 8.4.3 检视与补充流程

```
主行程规划完成（阶段5输出）
    ↓
添加辅助点位（美食、购物、夜生活）
    ↓
添加通行建议
    ↓
检视整体行程（8个维度）
    ↓
是否符合要求？
    ├─ 是 → 进入阶段7（预算计算）
    └─ 否 → 从候选景点池没入选和辅助点位中挑选穿插进去
        ↓
        重新检视
        ↓
        是否符合要求？
        ├─ 是 → 进入阶段7
        └─ 否 → 再次补充（最多3次）
            ↓
            3次后仍不符合 → 记录警告，进入阶段7
    ↓
后续暂不更改（阶段7、8、9不更改景点安排）
```

### 8.5 本阶段输出

完整行程，包含以下信息：
- 主行程（景点+时间线）
- 辅助点位（美食+购物+夜生活）
- 通行建议（景点间交通方式）
- 住宿推荐区域

## 9. 阶段7：预算计算与优化

### 9.1 阶段概述

**核心职责**：计算行程的各项预算（餐饮、住宿、交通、门票），并根据预算档位进行优化调整。

**输入**：完整行程

**输出**：带预算行程（餐饮+住宿+交通+门票+总预算）

### 9.2 预算计算规则

#### 9.2.1 餐饮预算

| 预算档位 | 每顿人均预算 |
|----------|--------------|
| 经济 | 30元 |
| 适中 | 80元 |
| 舒适 | 150元 |
| 奢华 | 300元 |

- 每天2顿正餐（午餐+晚餐）
- 早餐通常包含在住宿中，或单独计算（20-50元）
- 餐饮总预算 = 每顿预算 × 2顿 × 天数 × 人数

#### 9.2.2 住宿预算

| 预算档位 | 每间每晚预算 |
|----------|--------------|
| 经济 | 150元 |
| 适中 | 400元 |
| 舒适 | 800元 |
| 奢华 | 1500元 |

- 房间数根据人数计算（1-2人1间，3-4人2间，以此类推）
- 住宿晚数 = 天数 - 1（当天往返不需要住宿）
- 住宿总预算 = 每间预算 × 房间数 × 晚数

#### 9.2.3 交通预算

| 预算档位 | 每天人均交通预算 |
|----------|------------------|
| 经济 | 30元 |
| 适中 | 60元 |
| 舒适 | 120元 |
| 奢华 | 200元 |

- 市内交通按天计算
- 大交通（高铁/飞机）单独计算，根据出发地和目的地
- 交通总预算 = 每天交通预算 × 天数 × 人数 + 大交通费用

#### 9.2.4 门票预算

- 根据行程中包含的收费景点，累加门票价格
- 免费景点不计入
- 优惠政策（学生票、老人票、儿童票）根据人群计算

#### 9.2.5 总预算

总预算 = 餐饮预算 + 住宿预算 + 交通预算 + 门票预算

### 9.3 预算优化规则

#### 9.3.1 预算超支优化

如果计算出的总预算超过用户预算档位的预期范围：

1. **降低住宿档位**：选择更便宜的住宿区域
2. **减少收费景点**：增加免费景点，减少高价景点
3. **调整餐饮推荐**：推荐更平价的餐厅
4. **优化交通方式**：增加公共交通，减少打车

#### 9.3.2 预算不足优化

如果计算出的总预算远低于用户预算档位的预期范围：

1. **提升住宿档位**：选择更好的住宿区域
2. **增加收费景点**：增加高品质景点
3. **调整餐饮推荐**：推荐更高档的餐厅
4. **优化交通方式**：增加打车/专车

### 9.4 本阶段输出

带预算行程，包含以下信息：
- 餐饮预算（明细+总计）
- 住宿预算（明细+总计）
- 交通预算（明细+总计）
- 门票预算（明细+总计）
- 总预算
- 人均预算

## 10. 阶段8：LLM优化与文案生成

### 10.1 阶段概述

**核心职责**：使用LLM对行程进行智能优化，并生成出发语、每日灵感、回复文案、人文介绍等内容。

**输入**：带预算行程

**输出**：优化后行程（智能优化+人文介绍+出发语+每日灵感+回复文案）

### 10.2 LLM智能优化规则

#### 10.2.1 景点优化

1. **景点补充**：根据用户风格和兴趣，补充遗漏的重要景点
2. **景点替换**：将评分低、评价差的景点替换为更好的景点
3. **景点排序优化**：根据开放时间、人流高峰、最佳游览时间优化排序

#### 10.2.2 行程优化

1. **时间安排优化**：根据景点开放时间、游玩时长、交通时间优化时间安排
2. **用餐优化**：根据景点位置和人群推荐更合适的餐厅
3. **住宿优化**：根据行程安排推荐更合适的住宿区域

#### 10.2.3 人文介绍生成

为每个景点生成人文介绍：
1. **历史背景**：景点的历史沿革、重要事件
2. **文化价值**：景点的文化意义、艺术价值
3. **名人轶事**：与景点相关的名人故事、传说
4. **游览建议**：最佳游览路线、必看亮点、拍照建议
5. **语音介绍**：更详尽的语音介绍内容

### 10.3 文案生成规则

#### 10.3.1 出发语

生成富有感染力的出发语，激发行走天下的勇气：
- 示例："世界很大，从北京出发——这一步，就是行走天下的开始。"
- 与目的地相关，有感染力

#### 10.3.2 每日灵感

为每天生成一句旅行灵感：
- 示例："出发，是解决一切犹豫的办法。"
- 与当天主题相关，有启发性

#### 10.3.3 回复文案

生成对话式的回复文案，包含：
1. **行程概述**：目的地、天数、人群、风格、预算
2. **必去景点**：已安排的必去景点
3. **行程亮点**：行程的特色和亮点
4. **预算概览**：总预算和人均预算
5. **行动号召**：引导用户查看完整行程和地图
6. **调整提示**：提示用户可以调整行程

#### 10.3.4 品牌气质

在对话中体现品牌气质：
- 鼓励用户走出去，去旅行，去探索
- 激发行走天下的勇气
- 温暖、有感染力、不生硬

### 10.4 RAG知识检索规则

如果启用了RAG（检索增强生成）：

1. **检索时机**：
   - 用户询问景点人文介绍时
   - 用户询问历史名人、革命先辈相关信息时
   - 生成景点人文介绍时
2. **检索内容**：
   - 景点历史背景
   - 名人轶事
   - 文化价值
   - 游览建议
3. **知识干预**：
   - 后台可配置知识库内容
   - 人为干预检索结果，作为B端使用更灵活

### 10.5 本阶段输出

优化后行程，包含以下信息：
- LLM优化后的行程
- 每个景点的人文介绍
- 出发语
- 每日灵感
- 回复文案
- 语音介绍内容

## 11. 阶段9：验证与输出

### 11.1 阶段概述

**核心职责**：验证行程的合理性，然后格式化输出，存储到数据库，返回给前端。

**输入**：优化后行程

**输出**：最终行程（格式化、验证通过、已存储）

### 11.2 行程验证规则

#### 11.2.1 景点验证

1. **景点不重复**：行程中不出现重复的景点（主POI和子POI除外）
2. **景点开放**：所有景点在安排的时间内开放
3. **景点在中国**：所有景点都在中国境内
4. **必去景点包含**：must_include_poi中的景点都在行程中
5. **排除景点不包含**：exclude_poi中的景点都不在行程中

#### 11.2.2 时间验证

1. **时间不冲突**：景点之间时间不冲突
2. **游玩时长合理**：每个景点的游玩时长合理
3. **交通时间合理**：景点之间的交通时间合理
4. **用餐时间预留**：午餐和晚餐时间预留
5. **休息时间预留**：中间有适当的休息时间

#### 11.2.3 预算验证

1. **预算合理**：总预算在用户预算档位的合理范围内
2. **各项预算合理**：餐饮、住宿、交通、门票各项预算合理
3. **人均预算合理**：人均预算合理

#### 11.2.4 跨天验证

1. **跨天区域不重复**：不同天的景点不在同一区县（除非是跨城日）
2. **每天景点数量合理**：每天景点数量符合节奏配置
3. **住宿连续**：住宿区域连续，不频繁更换

### 11.3 验证失败处理

如果验证失败：

1. **自动修复**：对于可以自动修复的问题（如景点重复、时间冲突），自动修复
2. **降级处理**：对于无法自动修复的问题，降级处理（如减少景点数量、调整时间）
3. **记录日志**：记录验证失败的原因和处理方式
4. **返回警告**：在返回结果中包含警告信息

### 11.4 格式化输出规则

#### 11.4.1 数据结构

输出标准化的行程数据结构，包含：
- 基本信息（目的地、天数、人数、人群、预算、风格、节奏、出行方式）
- 每日行程（日期、主题、景点列表、时间线、餐饮、住宿、通行建议）
- 预算明细（餐饮、住宿、交通、门票、总计、人均）
- 人文介绍（每个景点的介绍）
- 文案（出发语、每日灵感、回复文案）

#### 11.4.2 地图数据

输出地图渲染所需的数据：
- 景点经纬度
- 路线坐标（每天的路线）
- 标记点信息
- 路线颜色（按天分色）

### 11.5 存储规则

1. **用户关联**：如果用户已登录，将行程与用户关联
2. **会话关联**：将行程与会话关联
3. **唯一ID**：生成唯一的行程ID
4. **创建时间**：记录创建时间
5. **更新时间**：记录更新时间

### 11.6 本阶段输出

最终行程，包含以下信息：
- 行程ID
- 完整的行程数据（已验证、已格式化）
- 地图渲染数据

### 12.1 数据流

```
阶段1输出：规划参数对象

阶段2输出：候选景点池
    ↓ 作为阶段3的输入
阶段3输出：景点聚类
    ↓ 作为阶段4的输入
阶段4输出：每日景点
    ↓ 作为阶段5的输入

    ↓ 作为阶段6的输入

    ↓ 作为阶段7的输入

    ↓ 作为阶段9的输入
阶段9输出：最终行程
```

### 12.2 反馈循环

某些阶段之间存在反馈循环：

1. **阶段2 → 阶段3**：如果聚类效果不好，返回阶段2重新筛选景点
2. **阶段4 → 阶段3**：如果按天分配后发现聚类不合理，返回阶段3重新聚类
3. **阶段5 → 阶段4**：如果排序后发现时间冲突，返回阶段4重新分配
4. **阶段7 → 阶段2**：如果预算超支，返回阶段2重新筛选景点（增加免费景点）
5. **阶段8 → 阶段5**：LLM优化后可能调整景点排序，返回阶段5重新排序

### 12.3 阶段优先级

当多个阶段的规则冲突时，按以下优先级处理：

1. **硬性约束**（最高优先级）：必去景点、排除景点、中国区域校验、开放时间
2. **用户明确指定**：用户明确指定的参数和要求
3. **阶段9验证规则**：行程验证规则
4. **阶段4分配规则**：按天分配和跨天去重规则
5. **阶段5排序规则**：每日排序和时间线规则
6. **阶段2筛选规则**：景点筛选规则
7. **阶段3聚类规则**：景点聚类规则
8. **其他规则**（最低优先级）：辅助点位、通行建议、预算优化
