# 行程规划引擎流程架构优化方案

> 本文档基于用户反馈，对现有行程规划引擎的39步流程进行重构优化，明确各阶段职责，解决数据冗余、顺序不合理、必要景点易被过滤等问题。
>
> **更新日期**：2026-08-31
> **状态**：待实施

---

## 一、现有流程的问题分析

### 1.1 阶段一问题

| 问题 | 说明 |
|---|---|
| 规则兜底干扰 | LLM识别失败时降级到规则解析，导致参数不稳定，且规则解析能力有限 |
| 天数非必填 | 天数缺失时使用默认值（2-3天），可能不符合用户实际需求 |
| 参数不完整直接生成 | 参数不完整时直接用默认值生成行程，而不是引导用户补全 |

### 1.2 阶段三问题

| 问题 | 说明 |
|---|---|
| 顺序不合理 | 先做行政区域补全，再做中国区域校验。如果目的地在境外，前面的行政区域补全就是无用功 |

### 1.3 阶段四问题（最严重）

| 问题 | 说明 |
|---|---|
| 多次补充POI | 步骤12（通用POI）、13（扩大搜索）、14（行政分级枚举）、15（主要景点注入）、16（必打卡注入）都是在增加POI数量，分散在多个步骤，逻辑不清晰 |
| 主要景点与必打卡作用重复 | 主要景点库（472个）和必打卡地标库都在注入景点，但职责边界不清晰 |
| 排除规则位置不合理 | 步骤17（排除POI）穿插在POI富化过程中，应该在候选池构建完成后统一应用 |
| 没有全量检索概念 | 每次检索都是增量补充，没有明确的"全量候选池"概念 |

### 1.4 阶段五和阶段六问题

| 问题 | 说明 |
|---|---|
| 筛选顺序不清晰 | 人群影响、大型景区识别、LLM优化、景区去重、通用去重、美食占比限制、地理聚类、体验曲线调整，筛选顺序没有明确的优先级逻辑 |
| 必要景点易被过滤 | 必打卡景点、用户指定景点在多次筛选中可能被误过滤 |
| 时间规划缺失 | 没有明确的"每个景点游览时长"规划步骤，时间线管理薄弱 |
| 兜底机制不清晰 | 景点不足时的补充逻辑分散在多个步骤，没有统一的兜底策略 |

## 二、优化后的流程架构

### 核心设计原则

1. **阶段四职责单一**：只负责构建全量候选池，做到"有数据可选"，不做任何筛选和排除
2. **必要景点优先保护**：必打卡、用户指定、主要景点在筛选前标记保护，确保不被过滤
3. **关联景点统一处理**：主POI和子POI的识别、去重、优先级调整统一在一个步骤完成
4. **地理聚类先行**：先按地理距离聚类，再做时间规划，确保同一天的景点地理位置相近
5. **时间规划独立**：每个景点的游览时长、每天的时间线管理独立成阶段
6. **时间跨度切分明确**：基于聚类和时间规划结果，按天分配景点
7. **兜底机制统一**：景点不足时，从候选池未入选景点中补充，最后用辅助POI（美食/购物）填充
8. **辅助POI最后填充**：景点填充完成后，再用美食、购物、夜生活等辅助POI填充空闲时间

| 步骤 | 数据转变 | 数据来源 | 说明 |
|---|---|---|---|
| 1.1 用户输入 | 原始文本消息 | 用户前端输入 | |
| 1.2 提取用户消息 | 从对话历史提取role=user的消息 | 前端对话历史 | |
| 1.3 LLM意图识别 | 原始文本 → `{intent, args, confidence}` | **本地LLM模型** | **去除规则兜底**，LLM不可用时直接提示用户重试 |
| 1.4 意图分类路由 | 根据intent分流：plan/chat/weather/poi | LLM输出 | |

**关键变化：**
- ❌ 去除规则兜底（LLM不可用时直接提示，不用规则解析）
- ✅ 天数改为必填参数
- ✅ 参数不完整时通过多轮对话引导用户补全，不直接生成行程

- ✅ 中国区域校验提前到行政区域补全之前，避免境外目的地的无用计算

### 阶段四：全量候选池构建（重构核心）

> **本阶段唯一职责：构建全量候选池，做到"有数据可选"，不做任何筛选和排除。**

| 步骤 | 数据转变 | 数据来源 | 说明 |
|---|---|---|---|
| 4.1 **全量POI检索** | 城市名 → 全量POI列表（景点/美食/购物/夜生活）<br>**一次性检索所有类别和所有行政级别**，不做增量补充 | **优先级**：DB POI缓存 → TTL缓存 → 腾讯API（翻页5页）→ 高德API | **合并**：原步骤12（通用POI）、13（扩大搜索）、14（行政分级枚举）合并为一次全量检索 |
| 4.2 **主要景点库注入** | 从主要景点库获取目的地主要景点，加入候选池<br>**作用：增强候选池质量，确保知名景点在候选池中** | **数据库** `major_attractions`表（472个） | **明确职责**：主要景点是候选池增强，不是强制规划 |
| 4.3 **必打卡地标注入** | 从必打卡地标库获取顶级地标，加入候选池<br>**作用：提供强制规划锚点，在后续筛选中标记保护** | **数据库** `must_visit_landmarks`表 | **明确职责**：必打卡是强制规划锚点，在阶段五标记保护 |
| 4.4 **候选池去重** | 基于坐标距离+名称相似度，对全量候选池去重 | 坐标距离（<200米）+ 名称相似度 | **新增**：在候选池构建阶段就做一次基础去重，减少后续处理量 |
| 4.5 **排除规则应用** | 根据exclude_poi参数排除指定景点 | 用户输入的exclude_poi | **顺序调整**：从步骤17移到候选池构建完成后，统一应用 |

**关键变化：**
- ✅ 合并多次POI检索为一次全量检索（原12、13、14合并）
- ✅ 明确主要景点（候选池增强）和必打卡（强制锚点）的不同职责
- ✅ 排除规则移到候选池构建完成后统一应用
- ✅ 新增候选池基础去重，减少后续处理量
- ❌ 本阶段不做任何筛选（人群、景区、LLM优化等都移到阶段五）

### 阶段五：必要景点保护与关联景点处理（新增阶段）

> **本阶段核心：确保必要景点不被过滤，处理主POI和子POI的关联关系。**

| 步骤 | 数据转变 | 数据来源 | 说明 |
|---|---|---|---|
| 5.1 **必要景点标记** | 标记必打卡景点、用户指定景点（must_include_poi）为"保护景点"<br>**保护景点在后续所有筛选中不被过滤** | 必打卡地标库 + 用户输入 | **新增**：统一标记保护景点 |
| 5.2 **大型景区识别** | 识别大型景区（如大明湖、西湖），标记景区内小景点<br>大型景区权重高，景区内小景点优先级降低 | **数据库** `large_scenic_areas`表 + 名称匹配 | 从原步骤19移到本阶段 |
| 5.3 **主POI/子POI关联处理** | 建立主景区和子景点的关联关系<br>**规则：如果主景区在候选池中，子景点只作为点位信息，不单独参与路径规划；如果主景区不在候选池中，子景点可以单独参与** | 大型景区识别结果 + 名称包含关系 | **新增**：统一处理主POI和子POI的关联 |
| 5.4 **主POI/子POI去重** | 如果主景区已在候选池，过滤掉该景区内的子景点（保留子景点信息作为主景区的点位） | 主POI/子POI关联关系 | 从原步骤23、24合并到本阶段 |
| 5.5 **通用POI去重** | 基于坐标距离+名称包含关系+名称相似度的智能去重<br>处理：同一景区不同命名、同一景点不同名称等 | 坐标距离（<200米）+ 名称相似度 | 从原步骤25移到本阶段 |

**关键变化：**
- ✅ 新增必要景点保护机制，确保必打卡和用户指定景点不被过滤
- ✅ 主POI和子POI的识别、关联、去重统一在一个阶段完成
- ✅ 明确规则：主景区在候选池时，子景点只作为点位信息，不单独参与路径规划

### 阶段六：景点筛选与地理聚类（重构）

> **本阶段核心：在保护必要景点的前提下，筛选优质景点，按地理距离聚类。**

| 步骤 | 数据转变 | 数据来源 | 说明 |
|---|---|---|---|
| 6.1 **人群影响规则** | 按人群类型标记景点友好属性，调整评分（友好景点+0.3分）<br>**注意：只调整评分，不做过滤** | **规则引擎** `GroupEngine` + 关键词匹配 | 从原步骤18移到本阶段，明确只调评分不过滤 |
| 6.2 **时间跨度收束** | 省级目的地按城市数量收束天数 | 候选景点的cityname统计 | 从原步骤20移到本阶段 |
| 6.3 **LLM智能优化** | LLM筛选景点+主题分组+建议时长<br>**注意：LLM只能从非保护景点中筛选，保护景点强制保留** | **本地LLM模型** + 候选景点数据 | 从原步骤21优化，增加保护景点约束 |
| 6.4 **LLM优化不足补充** | 如果LLM选中景点<days*2，从hot景点中补充（优先非景区内小景点）<br>**保护景点已在步骤6.3强制保留，此处只补充非保护景点** | 候选景点的hot标记和rating | 从原步骤22优化 |
| 6.5 **美食/购物/夜生活占比限制** | 根据策略配置调整点位类型比例<br>**注意：只限制辅助POI数量，不限制景点数量** | **策略配置** `poi_ratio` + 美食黑名单 | 从原步骤26优化，明确只限制辅助POI |
| 6.6 **地理聚类** | 按地理距离聚类成区域，近距离景点优先分配在同一天<br>**算法：以保护景点为锚点，其他景点按距离从近到远聚类** | 景点坐标（haversine距离）+ 聚类算法 | 从原步骤27优化，明确以保护景点为锚点 |

**关键变化：**
- ✅ 人群影响只调评分不过滤
- ✅ LLM优化增加保护景点约束（保护景点强制保留）
- ✅ 美食占比限制只限制辅助POI，不限制景点
- ✅ 地理聚类以保护景点为锚点
- ✅ 筛选顺序：人群评分 → 时间收束 → LLM筛选 → 不足补充 → 辅助POI限制 → 地理聚类

### 阶段七：时间规划与时间线管理（新增阶段）

> **本阶段核心：规划每个景点的游览时长，管理每天的时间线。**

| 步骤 | 数据转变 | 数据来源 | 说明 |
|---|---|---|---|
| 7.1 **景点游览时长估算** | 为每个景点估算游览时长（分钟）<br>**估算依据**：景点类型、评分、LLM建议时长、大型景区默认3-4小时、普通景点1-2小时 | 景点类型 + LLM建议时长 + 规则估算 | **新增**：独立的游览时长规划 |
| 7.2 **景点开放时间校验** | 校验景点开放时间，确保规划时间在开放时间内<br>**数据来源**：POI数据中的营业时间字段，缺失时使用默认时间（08:00-18:00） | POI营业时间 + 默认时间 | **新增**：开放时间校验 |
| 7.3 **每天时间线模板** | 根据策略配置生成每天的时间线模板<br>**模板包含**：出发时间、上午时段、午餐时间、下午时段、晚餐时间、返回时间 | **策略配置** 起止时间 + 体验曲线 | **新增**：时间线模板 |
| 7.4 **景点间交通时间估算** | 估算景点间的交通时间（分钟）<br>**估算依据**：地理距离 × 出行方式平均速度（步行5km/h、公交20km/h、打车30km/h、自驾40km/h） | 景点坐标距离 + 出行方式参数 | **新增**：交通时间估算 |

**关键变化：**
- ✅ 新增独立的时间规划阶段
- ✅ 每个景点的游览时长、开放时间、交通时间都有明确规划
- ✅ 每天的时间线有模板管理

### 阶段八：时间跨度切分与行程构建（重构）

> **本阶段核心：基于聚类和时间规划结果，按天分配景点，构建完整行程。**

| 步骤 | 数据转变 | 数据来源 | 说明 |
|---|---|---|---|
| 8.1 **按天分配景点** | 基于地理聚类结果，将景点分配到不同天<br>**分配规则**：<br>1. 保护景点优先分配（必打卡景点分散到不同天）<br>2. 同一聚类的景点优先分配在同一天<br>3. 每天景点总时长不超过时间线模板的可用时长<br>4. 跨天不重复（同一景点不出现多次） | 地理聚类结果 + 时间规划结果 + 保护景点标记 | 从原步骤27、28、29重构 |
| 8.2 **跨天地域去重** | 确保不同天的景点不在同一子区域 | 景点的district/cityname字段 | 从原步骤31保持 |
| 8.3 **体验曲线调整** | 根据体验曲线调整每天的景点强度和数量<br>**注意：调整时保护景点不被移除，只调整非保护景点** | **规则引擎** 体验曲线 + 景点强度关键词 | 从原步骤32优化，增加保护景点约束 |
| 8.4 **行程时间线填充** | 将分配到每天的景点填入时间线模板<br>**填充规则**：按地理顺序排列，计算每个景点的起止时间，预留交通时间和用餐时间 | 时间线模板 + 景点游览时长 + 交通时间 | **新增**：明确的时间线填充步骤 |
| 8.5 **住宿区域推荐** | 每天景点聚类中心 → 推荐住宿区域（不推荐具体酒店） | 景点坐标聚类中心 | 从原步骤36保持 |

**关键变化：**
- ✅ 按天分配时明确保护景点优先
- ✅ 体验曲线调整时保护景点不被移除
- ✅ 新增行程时间线填充步骤，每个景点有明确的起止时间

### 阶段九：兜底处理与辅助POI填充（新增阶段）

> **本阶段核心：景点不足时的兜底补充，以及辅助POI（美食/购物/夜生活）的填充。**

| 步骤 | 数据转变 | 数据来源 | 说明 |
|---|---|---|---|
| 9.1 **景点充足性校验** | 校验每天的景点数量和总时长是否满足要求<br>**校验标准**：每天至少2个景点，总时长不少于4小时 | 行程构建结果 | **新增**：明确的充足性校验 |
| 9.2 **候选池补充** | 如果景点不足，从候选池未入选景点中补充<br>**补充优先级**：<br>1. 保护景点（如果还未入选）<br>2. 高评分景点<br>3. 地理位置相近的景点 | 候选池未入选景点 + 评分 + 地理距离 | **新增**：统一的候选池补充机制 |
| 9.3 **实时POI补充** | 如果候选池补充后仍不足，调用第三方地图API实时检索补充<br>**检索范围**：以当天景点聚类中心为圆心，半径5公里内的景点 | 腾讯/高德地图POI搜索API（实时调用） | **新增**：实时POI补充（最后手段） |
| 9.4 **辅助POI填充** | 景点填充完成后，用美食、购物、夜生活等辅助POI填充空闲时间<br>**填充规则**：<br>1. 午餐时间填充美食（景点附近）<br>2. 晚餐时间填充美食（景点附近或住宿区域附近）<br>3. 空闲时间填充购物/夜生活（根据策略配置）<br>4. 辅助POI不参与路径规划，只作为时间填充 | 候选池中的美食/购物/夜生活POI + 地理距离 | **新增**：明确的辅助POI填充阶段，在景点填充完成后 |
| 9.5 **极端兜底** | 如果以上步骤都无法满足，生成最简行程（每天1-2个核心景点） | 城市中心坐标 + 主要景点库 | 从原步骤30（_emergency_plan）优化 |

**关键变化：**
- ✅ 明确的兜底处理顺序：候选池补充 → 实时POI补充 → 极端兜底
- ✅ 辅助POI填充在景点填充完成之后，不参与路径规划
- ✅ 辅助POI只作为时间填充（午餐、晚餐、空闲时间）

## 三、优化前后对比

### 流程步骤对比

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 总阶段数 | 7个 | 10个 |
| 总步骤数 | 39步 | 约45步（但逻辑更清晰） |
| 候选池构建 | 6步，分散多次补充 | 5步，一次全量检索+统一注入 |
| 必要景点保护 | 无明确机制 | 独立阶段（阶段五），统一标记保护 |
| 主POI/子POI处理 | 分散在3个步骤 | 统一在阶段五完成 |
| 时间规划 | 无独立阶段 | 独立阶段（阶段七），游览时长/开放时间/交通时间 |
| 兜底处理 | 分散在多个步骤 | 独立阶段（阶段九），明确补充顺序 |
| 辅助POI填充 | 与景点混合筛选 | 独立步骤，在景点填充完成后 |

### 核心改进点

| 改进点 | 说明 |
|---|---|
| 1. 去除规则兜底 | LLM不可用时直接提示，不用规则解析，避免参数不稳定 |
| 2. 天数必填+多轮补全 | 参数不完整时通过对话引导用户补全，不直接生成 |
| 3. 中国区域校验提前 | 避免境外目的地的无用计算 |
| 4. 全量候选池构建 | 合并多次POI检索，明确候选池概念，本阶段不做筛选 |
| 5. 必要景点保护机制 | 必打卡和用户指定景点标记保护，后续所有筛选不过滤 |
| 6. 主POI/子POI统一处理 | 识别、关联、去重统一在一个阶段完成 |
| 7. 独立时间规划阶段 | 游览时长、开放时间、交通时间、时间线模板都有明确规划 |
| 8. 明确兜底顺序 | 候选池补充 → 实时POI补充 → 极端兜底 |
| 9. 辅助POI最后填充 | 景点填充完成后，再用美食/购物填充空闲时间 |
| 10. 筛选顺序清晰 | 人群评分 → 时间收束 → LLM筛选 → 不足补充 → 辅助POI限制 → 地理聚类 |
