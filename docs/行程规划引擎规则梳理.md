# 行程规划引擎规则梳理（当前版本）

> 文档版本：v1.0  
> 更新时间：2026-08-29  
> 适用范围：`backend/app/core/planner.py` 及 `backend/app/services/planner/` 模块

---

## 1. 规划引擎概述

### 1.1 核心定位
行程规划引擎采用 **"AI 生成 + 规则引擎兜底 + 高德路径/预算增强"** 的混合架构，支持两种规划策略：
- **traditional（传统策略）**：直接按天分配景点
- **spatial_temporal（两阶段策略）**：先空间整体路线规划，再按时间拆分

### 1.2 规划主流程
```
用户输入 → 意图识别 → 目的地定位 → 中国区域校验 → 候选POI检索 → 行政分级枚举景点
→ 必打卡地标注入 → 大型景区识别 → 时间跨度收束 → LLM智能优化 → 主/子POI去重
→ 地理规划（聚类→切分→排序）→ 辅助点位补充 → 预算计算 → 结果输出
```

### 1.3 核心模块
| 模块 | 路径 | 职责 |
|------|------|------|
| 主入口 | `core/planner.py` | `build_plan()` 主函数，协调各模块 |
| 地理枚举 | `services/planner/geo_enum.py` | 行政分级枚举景点、中国区域校验 |
| 必去地标 | `services/planner/must_visit.py` | 从数据库注入必打卡地标 |
| 聚类 | `services/planner/cluster.py` | 景点地理聚类、区域分配 |
| 逐日构建 | `services/planner/daily_build.py` | 按天分配景点、排序、辅助点位补充 |
| 两阶段规划 | `services/planner/spatial_temporal_planner.py` | 先空间整体路线，再时间拆分 |
| 常量配置 | `services/planner/planner_constants.py` | 聚类距离、范围等常量 |
| 工具函数 | `services/planner/utils.py` | 预算表、节奏配置、出发语等 |

## 2. 景点筛选规则

### 2.1 候选POI检索
**规则**：
- 调用高德/腾讯POI搜索，检索类别：`["景点", "美食", "购物", "夜生活"]`
- 如果检索结果为空，使用兜底景点（`_fallback_pois`）
- 应用用户排除规则（`exclude_poi`）

**问题**：
- POI搜索排序不准，热门景点可能排在后面
- 缺少景点热度、评分、评论数等综合排序依据

### 2.2 行政分级枚举景点
**规则**：
- **目的地为省级**：枚举省内各市的景点，按市分隔做路径规划
- **目的地为市级/区级/地点级**：
  1. 先把当前市级/区级/地点作为1级推荐
  2. 再往上枚举至当前地归属省下的地点作为补充
- 枚举范围：区/县 → 市 → 省

**实现**：`_enumerate_scoped_attractions(geo, center)`

**问题**：
- 枚举逻辑复杂，效果不稳定
- 可能枚举到无关景点

### 2.3 必打卡地标注入
**规则**：
- 从数据库 `must_visit_landmarks` 表中注入必去地标
- 注入时机：在时间跨度收束与规划之前，确保基于完整景点池

**实现**：`_inject_must_visit_attrs(destination, attrs)`

**问题**：
- 必去地标库覆盖不全
- 部分城市的必去地标可能缺失

### 2.4 LLM智能优化
**规则**：
- 如果AI可用且有候选景点，调用 `ai_mod.optimize_itinerary()` 进行智能优化
- 优化内容：POI筛选 + 主题分组 + 建议时长
- LLM选中的景点注入优化字段（`llm_duration`、`llm_theme`、`llm_best_slot`、`llm_reason`）
- 如果LLM选中的不足，从hot景点中补充（按评分排序）

**数量控制**：
- 最少需要：`days × 2` 个景点
- 最多总数：`days × 5` 个景点

**问题**：
- LLM优化效果不稳定
- 可能筛选掉热门景点

### 2.5 排除规则
**规则**：
- 用户明确排除的景点（`exclude_poi`）不入选
- 在候选POI检索和行政分级枚举后分别应用排除规则

## 3. 主POI和子POI分配规则

### 3.1 大型景区识别
**规则**：
- 基于静态数据识别大型景区（如大明湖、西湖、故宫）
- 静态数据来源：`data/static/large_scenic_areas.py`
- 识别函数：`is_large_scenic_area(name, category)`

**问题**：
- 静态数据覆盖不全，很多大型景区识别不到
- 识别逻辑简单，仅基于名称匹配

### 3.2 子POI标记
**规则**：
- 景区内小景点标记为 `is_scenic_inner=True`
- 记录父景区名称 `parent_scenic`
- 识别函数：`is_inside_large_scenic_area(name, category)`

**问题**：
- 仅基于静态数据识别，覆盖不全
- 很多景区内小景点无法识别

### 3.3 权重调整
**规则**：
- 大型景区权重因子：`get_scenic_area_weight_factor(name, category)`
- 景区内小景点优先级降低，不单独参与跨景区路径规划

### 3.4 去重逻辑
**规则**：
1. **LLM优化后的去重**：
   - 如果大型景区本身已被选中，过滤掉该景区内的小景点
   - 也检查名称包含大型景区名的情况（如"大明湖景区"包含"大明湖"）
2. **统一去重**：
   - `dedup_scenic_inner_pois(attrs, request_id, destination)`
   - 确保所有路径都生效

**问题**：
- 静态数据覆盖不全，很多主/子POI关系无法识别
- 去重逻辑复杂，可能误删景点

### 3.5 三层POI数据挂载
**规则**：
- 规划完成后，为主景点附加内部游览动线和周边附属点位
- 数据来源：数据库 `poi_hierarchy` 表
- 挂载函数：`_mount_poi_hierarchy(day_plans, known)`

**挂载内容**：
- `inner_route`：景区内部游览动线
- `nearby_attractions`：周边附属点位（美食街/老街/市井等）
- `poi_level`：景区级别（5A/4A/无）
- `recommended_duration`：建议游玩时长
- `best_time`：最佳游玩时间
- `avoid_tips`：避坑提示
- `description`：景点描述
- `has_hierarchy`：是否有三层POI数据

## 4. 聚类规则

### 4.1 聚类目标
把地理位置相近的景点聚为一组，避免来回跑。

### 4.2 聚类维度
- **地理距离**（主要）：基于经纬度的距离聚类
- **行政区域**（辅助）：如同一区县
- **主题**（辅助）：如都是博物馆

### 4.3 聚类算法
**实现**：`services/planner/cluster.py`

**核心函数**：
- `cluster_attractions(attrs)`：景点地理聚类
- `merge_sparse_clusters(clusters)`：合并稀疏聚类
- `make_area(cluster)`：生成区域
- `greedy_group(...)`：贪心分组
- `split_to_balance(...)`：平衡拆分
- `dist_tier(dist)`：距离分级
- `assign_areas_to_days(...)`：分配区域到天
- `area_label(area)`：区域标签

**常量配置**：
- `CLUSTER_MAX_DIST`：聚类最大距离
- `SCOPE_MAX_RANGE`：范围最大距离

**问题**：
- 聚类算法不透明，效果不稳定
- 聚类参数可能需要根据城市规模调整

### 4.4 聚类结果
- 每个聚类对应一个"区域"
- 每个区域有一个中心点（用于路线规划）
- 每个区域有一个标签（如"皇城经典"、"皇家园林"）

## 5. 切分规则（按天分配）

### 5.1 切分目标
把聚类合理分配到每天，考虑时间、交通、体力。

### 5.2 切分维度
- **天数**：用户指定
- **每天景点数量**：根据节奏调整（轻松/适中/暴走）
- **每天总游玩时长**：根据节奏调整
- **跨天区域不重复**：避免同一天区域重复出现在不同天

### 5.3 切分算法
**传统策略（traditional）**：
- 直接按天分配景点
- 实现：`_geo_plan(req, center, pois, attrs, is_province)`

**两阶段策略（spatial_temporal）**：
- 先空间整体路线规划，再按时间拆分
- 实现：`_spatial_temporal_plan(req, origin_geo, center, return_geo, attrs, pois)`

**核心函数**：
- `assign_areas_to_days(...)`：分配区域到天
- `split_to_balance(...)`：平衡拆分
- `greedy_group(...)`：贪心分组

### 5.4 时间跨度收束
**规则**：
- 按实际可支撑的区域（市/聚类区）数上限收束天数
- 避免"规划点不足（天数多于可去地点）"或"过于庞杂（天数远超可分配区域）"
- 年/月/日维度的归一化与15天上限已在意图层完成

**实现**：
```python
if is_prov:
    n_regions = len({(p.get("cityname") or "").replace("市", "").strip()
                     for p in attrs if p.get("cityname")}) or 1
else:
    n_regions = max(1, len(_cluster_attractions(attrs)))
if req.days > n_regions:
    req.days = n_regions
```

### 5.5 跨天区域去重
**规则**：
- 仅对非geo路径生效（geo路径已按子区域天然不重复）
- 实现：`_enforce_region_distinct(req, center, all_candidates, day_plans)`

### 5.6 天数不足补齐
**规则**：
- 如果天数不足，用规则引擎补齐
- 候选池 = 景点 + 辅助池
- 实现：`_ensure_days(req, center, all_candidates, day_plans)`

## 6. 排序规则（每天内的景点顺序）

### 6.1 排序目标
每天内的景点顺序合理，避免来回跑，考虑开放时间。

### 6.2 排序维度
- **地理距离**（主要）：就近优先
- **开放时间**（辅助）：如早上去看升旗
- **游玩时长**（辅助）：大景点安排在上午
- **交通便利性**（辅助）：地铁沿线优先

### 6.3 排序算法
**实现**：`services/planner/daily_build.py`

**核心函数**：
- `reorder_day(day_plan, center)`：重新排序一天的景点
- `build_items(...)`：构建行程项
- `apply_timeline(...)`：应用时间线

**问题**：
- 排序算法简单，主要基于地理距离
- 没有充分考虑开放时间、游玩时长、交通时间

### 6.4 时间线应用
**规则**：
- 每天有固定的时段模板（早餐、上午、午餐、下午、晚餐、晚上）
- 实现：`apply_timeline(day_plan, req)`
- 常量：`SLOT_ORDER`、`SLOT_TIME`

**时段模板**：
| 时段 | 时间 | 内容 |
|------|------|------|
| 早餐 | 07:00-09:00 | 美食 |
| 上午 | 09:00-12:00 | 景点 |
| 午餐 | 12:00-14:00 | 美食 |
| 下午 | 14:00-17:00 | 景点 |
| 晚餐 | 17:00-19:00 | 美食 |
| 晚上 | 19:00-21:00 | 夜生活/购物 |

## 7. 辅助点位规则（美食/购物/夜生活）

### 7.1 辅助点位定位
辅助点位只做补充，不干扰主要景点规划。

### 7.2 美食推荐
**规则**：
- 午餐/晚餐时间就近推荐
- 根据用户预算和口味筛选
- 每天1-2个美食推荐
- 实现：`pick_auxiliary(...)`、`local_aux(...)`

### 7.3 购物推荐
**规则**：
- 下午或晚上就近推荐
- 根据用户偏好筛选
- 不作为主要规划点

### 7.4 夜生活推荐
**规则**：
- 晚上就近推荐
- 根据用户偏好筛选
- 每天最多1个夜生活推荐

### 7.5 辅助点位不参与跨天去重
同一天可以有多个辅助点位。

## 8. 其他规则

### 8.1 中国区域校验
**规则**：
- 仅规划中国境内目的地
- 境外目的地返回拒绝信息
- 实现：`_is_in_china(geo)`

### 8.2 大时间跨度规划
**规则**：
- 时间跨度以月/年为单位时，生成月度分配摘要
- 按省/月合理分配
- 实现：`_build_long_span_summary(req, province)`

**月度分配逻辑**：
- 以年为单位：按省规划，哪个月是这个省比较好的出行时间就安排在哪个月
- 以月为单位：1个月规划当前省或临近省，2个月安排2个省

### 8.3 预算计算
**规则**：
- 每天预算根据档位（经济/适中/舒适/奢华）和人数计算
- 总预算 = 每天预算之和
- 实现：`day_budget(...)`、`total_breakdown(...)`

**预算表**：`BUDGET_TABLE`（定义在 `services/planner/utils.py`）

### 8.4 节奏配置
**规则**：
- 根据用户节奏（轻松/适中/暴走）调整每天景点数量和游玩时长
- 不同人群有默认节奏：亲子/老人→轻松，单人/情侣/家庭→适中，朋友→暴走
- 实现：`PACE_ITEMS`、`GROUP_PACE`

### 8.5 出发语和每日灵感
**规则**：
- 每次规划生成个性化出发语
- 每天生成一句旅行灵感
- 实现：`departure_message(...)`、`daily_inspiration(...)`

## 9. 当前规则的问题和局限性

### 9.1 景点数据质量
- POI搜索排序不准，热门景点可能排在后面
- 必去地标库覆盖不全
- 缺少景点热度、评分、评论数等综合排序依据

### 9.2 主POI和子POI识别
- 静态数据覆盖不全，很多大型景区识别不到
- 很多景区内小景点无法识别
- 去重逻辑复杂，可能误删景点

### 9.3 聚类和切分
- 聚类算法不透明，效果不稳定
- 聚类参数可能需要根据城市规模调整
- 切分逻辑复杂，效果不稳定

### 9.4 排序和时间安排
- 排序算法简单，主要基于地理距离
- 没有充分考虑开放时间、游玩时长、交通时间
- 没有真实路径规划，点与点直线连接

### 9.5 辅助点位
- 美食/购物/夜生活推荐不够智能
- 没有结合用户口味、预算、位置

### 9.6 个性化
- 个性化程度低，主要基于用户风格（美食/人文/网红/小众）
- 没有用户画像、历史行程、兴趣标签等深度个性化

## 10. 优化方向建议

### 10.1 第一优先级（立即可做，效果明显）
1. **优化POI搜索排序**：优先返回热门、高评分景点
2. **完善必去地标库**：增加热门城市的必去景点
3. **主POI和子POI去重**：大景区内的子景点只作为点位，不作为主要规划点

### 10.2 第二优先级（中期优化，提升体验）
4. **考虑景点开放时间**：避免安排闭馆景点
5. **考虑建议游玩时长**：合理安排每天景点数量
6. **优化每天景点顺序**：按地理位置最优排序

### 10.3 第三优先级（长期优化，个性化）
7. **真实路径规划**：调用路径规划API计算交通时间
8. **通行建议**：景点之间推荐交通方式
9. **智能住宿推荐**：结合行程位置推荐住宿区域
10. **深度个性化**：用户画像、历史行程、兴趣标签
